# 常驻编译请求

`zil check FILE --resident --json` 和 `zil build FILE --resident --json` 在一个进程中复用已有 `CompilationSession` 的未验证快照，避免每次从进程启动和磁盘恢复开始。其余编译参数与普通 check/build 共用解析与约束；构建仍使用选择的原后端和优化级别。模式必须显式开启，不改变普通命令，不启动网络服务、不监视文件、不执行生成程序。

启动时输出一行 `{"ready":true,"protocol":1,...}`。客户端向标准输入发送 `compile`、`clear`、`stats` 或 `quit`，每条命令以换行结束；兼容 CRLF，单行最多32字节。每次 `compile` 返回一行包含原编译 `report` 的JSON：失败仍返回当前诊断，客户端不能根据进程仍存活或旧输出文件存在判断成功。成功请求不复用旧Verify授权；达到Verify的请求始终执行当前独立验证。`clear` 丢弃会话内全部历史，`stats` 返回当前缓存数量及可用的RSS观测，`quit` 或输入EOF结束进程。未知或不完整命令以协议错误结束。

请求重新读取源码、显式项目清单/锁及语法提供者锁；声明、导入和依赖变化不能仅因进程常驻而视为未变化。`--compile-timeout-ms` 每个请求重新起算。固定命令参数不能在消息中改变；切换目标、后端或配置须启动另一个进程。调用者须在请求期间提供一致的文件快照，与单次CLI相同；此接口不是原子多文件编辑事务。

默认最多保留32个raw查询项；`--resident-capacity 8..256` 可调整。每64次编译请求自动丢弃整个会话，`--resident-reset-after 1..4096` 可调整，显式clear不受此计数限制。这些是缓存项和历史寿命界限，不是总字节/RSS硬限额；单个请求仍受原有Limits约束，分配器也可能保留已释放的物理页。Linux报告当前RSS和峰值，其他平台无观测时为null。需要严格进程内存上限的宿主应另施操作系统资源限制。

常驻复用不等于无修改Fresh跳过：真实请求仍重新检查当前输入，执行所需分析、Verify及链接。评测须区分冷进程启动与热请求，完整计入消息往返、缓存清空及输出，并同时记录内存；不能把常驻收益表述为更换后端、缓存安全授权或已经实现完整函数级增量链接。
