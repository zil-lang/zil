### 170：父字段只承接完整数组责任

父Package每个拥有字段有实际责任旗标，一个数组字段旗标代表该完整数组。整字段取出后，数组成为已有固定数组局部，才使用静态元素取走/补入；数组缺元素时不能补回父字段。字段替换先准备完整新值，再清旧字段并提交。失败准备清理真正已获得的临时责任，保留尚未被显式消费的旧字段。

完整父壳可继续作为固定数组元素或拥有错误载荷，递归销毁按父字段声明序、数组下标递增序执行。没有通过地址是否相等来合并零尺寸元素责任；独立原生输入验证了零尺寸资源与重复取出/补回均不会重复或漏掉析构。

作者限定11组116项通过；独立重跑新增16项，并额外运行4项边界测试，包括4次O0/O2原生观察和私有字段、活动借片精确拒绝。作者三入口消费者另有26次原生执行。上述计数分别属于不同运行，不能相加冒充独立覆盖。

### 171：共享头指向原来的载体

内部形状是精确的 `Address<Managed<Record<R>>>`，沿用实际局部地址与字段投影；一般地址pointee分类没有因此接受任意Managed值。Verify重建实际头/Desc来源、存活、贷款、跨调用写效果和责任转交；整体ReadAddress/WriteAddress仍不能复制或覆盖Managed头。

作者17项限定测试包含24次原生执行，CLI样例另有4次；27个源码近邻与9组raw/wire反例拒绝。独立审核重跑17项，并添加5个异形探针、8次原生执行和额外raw/wire/预算检查。LLVM核对确认实际单份内联载体，地址转交没有制造第二个头，清理前先撤销live标志。

本轮实际发现Desc-only helper内部构造并调用闭包时的写效果漏传，以及捕获地址的最后一次调用活性问题。效果传播和当前调用活性已修复；**含实际头窗口模块的Desc+Address混合捕获回调仍明确Verify/Unsupported**，等待逐捕获读写与重借入合同。无头窗口的原Copy地址加Desc闭包、异源纯Desc回调和无关自含拥有闭包有保留的通过对照。可重赋值资源经既有私有Package槽降低后的头借用也仍关闭。

### 172：Store拥有初始化前缀

源码使用 `Store<T>`，默认是描述模式；`store_new()`需要上下文中的具体Store类型。普通函数工厂显式声明create结果，完整转交使用give。六个裸原语为 `store_new`、`store_reserve`、`store_push`、`store_pop`、`store_len`、`store_capacity`。

| 操作 | 已实现合同 |
|---|---|
| 空构造 | 不分配，只建立空头 |
| reserve | 请求绝对元素容量，先检查负数及stride乘积范围；失败保持原头、元素、len和cap |
| push | 消费一个完整T；不自行分配；满时以`T!void`错误分支返回完整未插入元素 |
| pop | 有元素时先减少len再转交原尾元素，返回`void!T`；空时为void错误 |
| 转交 | 完整头移动一次转交整个初始化前缀的责任 |
| 销毁 | 先撤销外层责任，再按索引升序清理`[0,len)`，每个Package按字段声明序清理，最后释放存储块 |

运行时长度不会在编译器里展开为cap个静态槽。未初始化尾部没有元素责任，已pop的旧槽位不再析构。Store有自己的密封类型和精确定义，不把ByteBuffer字节操作重解释为任意元素容器；只复用既有显式allocator ABI。

作者15项定向测试、相交170回归16项通过，包含20次suite原生执行、19项精确源码拒绝及22组raw/wire拒绝。四模块消费者另有12次普通、22次实际分配探针；分配准备点1–6逐一失败注入，均`allocated == frees`、`live == 0`。独立审核重跑15项，另写5项探针、4次普通及4次allocator执行，覆盖宽布局、多个析构字段、非零载荷上的零尺寸资源、满push归还、扩容失败恢复及失效描述。

## 真正组合后的三个入口

源码位于 `examples/mainline/zui_language173/`，共7个源文件；主入口实际加载5个模块，另外两个入口各加载3个。`tools/language/173/consumer.py`使用真实编译器和Clang，且每个成功构建必须独立Verify一次。测试用allocator观察器在main前注册退出报告，零分配路径也有实际计数。

| 入口与输入 | 普通O0/O2输出 | 退出码 | 验证重点 |
|---|---|---:|---|
| main，0项 | HZCBA | 0 | 空Store、真实共享头、数组字段状态及保存回调 |
| main，1项 | DHZCBA | 0 | 一次push/pop与父壳责任 |
| main，3项 | FEDHZCBA | 0 | 运行时数量、尾取逆序与普通helper |
| main，4项 | GFEDHZCBA | 0 | 同一合同下更长前缀 |
| main，非法输入9 | 空 | 9 | 输入拒绝前不构造拥有状态 |
| main，Store分配失败 | ZCBA | 1 | 已有字段/已取值清理，回调尚未创建 |
| prepare_failure | DCZAB | 1 | 新数组后续元素失败，原父字段完整保留并清理 |
| field_exit | ABZ | 1 | 整字段已取出时，父壳只清剩余责任 |

prepare_failure的分配失败位置1–4分别输出AZ、BAZ、CZAB、DCZAB；field_exit的位置1–2输出AZ、BAZ。30次探针执行全部释放成功分配，最终live为零。

非作者先独立推导这些顺序，再复跑全部44次；另外编写不含Store的四模块拥有错误ABI/保存FnMut与双拥有错误载荷程序，共12次原生执行和8个精确语义反例。它们专门核查173推导修复没有误开错误联合捕获、非Copy闭包ABI、借入/嵌套载荷或重复消费。

## 公共接口审核中真实发现的问题

- `Store`及原语保留名曾可通过名义声明、泛型绑定或别名消除绕过。修复已前移至正规化之前；成员同名保持合法。独审原样复跑7个非法占名，公共IR与Expand61项通过。
- 深层原始类型在Wire递归Writer/Reader中可先耗尽宿主线程栈。现在使用有界显式任务栈，保持所有标签、字节顺序及节点/集合/深度收费。独审覆盖36个手工字节格式oracle、全部类型标签、精确N/N−1、1,442个截断输入及128KiB线程的255/256/258层边界；没有提高默认预算。
- 普通`Item!void`等拥有错误helper在无关保存闭包触发的上下文推导中被旧白名单误拒。只补入已有`errors::owned`精确谓词，完整类型仍先收费后复制，后续拥有与capture核验保持独立。

完整回归的第一次构建因磁盘不足在链接阶段失败，未执行测试；重建仅关闭Rust调试符号，不改优化级别、调试断言或语言预算。其后发现047/147/163旧共享头拒绝预期，以及三处旧拒绝措辞，与真实新增行为不符；原输入保持，严格迁移接受性/阶段/诊断预期后重新完整跑到1526通过。所有原失败单独保留，不覆盖成Pass。

## 原样探针与尚未闭合的ZUI前置

原159脚本SHA仍为 `1acf26ce2b3b74629a4936d74ab0f943ce71d6751f1843c2a3a64d7241520f45`。嵌套拥有回调、泛型trait约束、真实资源`&Self`声明、捕获闭包数组现为Success并Verify一次。直接资源数组仍因默认Desc与Managed构造模式不匹配SafeReject；直接拥有ByteBuffer错误结果仍Unsupported。Package包装的成功不替换这两个原始输入。

最优先的下一批是：**Store进入长期State拥有字段、动态前缀的安全只读访问、具体自含回调字段**。此外必须保留Win64 Store、混合捕获效果精度、字段资源头、外部保留回调注销/重入/排空等实际缺口。详细三线建议、最小消费者和近邻反例见 [174起接续](NEXT-LANGUAGE-174.md)。本轮成果可以继续搭建语言消费者，不宣称ZUI之前所有语言前置已经清零。
