# `?` 符号族：三个候选的全场景比较

状态：2026-10-23。**当前主线为 ZIL-LANG-1.3/A，`&T? = (&T)?`。** 用户要求继续比较终态的一致性与割裂感；018 前缀 parser 是未合入的实验，不代表已选择前缀或已发布新语言版本。语言规则仍以 `_zil_design.md` 与 `spec/grammar.ebnf` 为准，本文不是第二份规范。

## 当前结论与比较边界

并列保留 A（后缀可空、借用先结合）、B（常规后缀优先）、C（Zig 风格前缀可空）三个候选。**目前没有单一方案被证明是全场景赢家。** A 的可选借用短，B 的类型和表达式结合方向相近，C 的前缀类型构造层次直接可见；这些局部优点尚不能替代完整程序的阅读比较。

用户已经排除旧源码兼容成本。保持主线 A 是当前施工状态，不是因已有实现而预先判 A 获胜；018 已写出前缀 parser，也不是判 C 获胜的证据。终态选定后直接修正当前语言和源码，不为兼容同时保留多套可空拼写。

三案必须使用同一批类型、表达式和完整小程序，采用相同的箭头范围、借用语义、错误规则和诊断要求。函数整体是否可以省括号、是否允许 Option 传播、链终点是否吸收已有 Option 层，都要作为独立维度比较，不能只给其中一案增加语法便利后再计算其优势。

## 三案的阅读方式

| 方案 | 较一致的部分 | 需要解释的部分 |
|---|---|---|
| A：后缀可空，借用先结合 | `T?` 与 `?.`、`??` 的视觉位置接近；`&T?` 简写可选借用 | 类型 `&T? = (&T)?`，表达式 `&x? = &(x?)`，相同符号顺序的组合边界不同 |
| B：后缀可空先结合 | 类型后缀和表达式后缀都先于借用；`&T?`、`&x?` 的树形顺序相近 | 可选借用需 `(&T)?`；位置接近仍不意味着类型构造与传播具有相同语义 |
| C：前缀可空 | `?&T` / `&?T` 按外到内表达类型层次 | 类型问号前置，链访问、默认与既有错误传播仍在值后或值之间；类型 `??T` 与表达式 `a ?? b` 需按语法位置区分 |

若优先避免类型/表达式结合方向的例外，B 值得认真比较；若优先按外到内阅读一元类型构造，C 有优势；若可选借用的常用性足以承担一条显式例外，A 仍有理由。当前没有同一批源码的频率和误读证据，不能把偏好写成测量结果，也不设置未经测量的百分比权重。

### 同一类型含义的写法

以下 B/C 写法仅用于候选比较，不是主线接受的别名。函数整体在三列中一律显式分组；箭头右侧一律取完整返回 Type。其他复合类型也尽量显式分组，以免混入尚未共同评估的省括号规则。

| 含义 | A：借用先结合 | B：常规后缀优先 | C：前缀 |
|---|---|---|---|
| 可空值 | `T?` | `T?` | `?T` |
| 可选共享借用 | `&T?` | `(&T)?` | `?&T` |
| 共享借用可空槽位 | `&(T?)` | `&T?` | `&?T` |
| 可选独占借用 | `&mut T?` | `(&mut T)?` | `?&mut T` |
| 独占借用可空槽位 | `&mut (T?)` | `&mut T?` | `&mut ?T` |
| 可选带借入期的借用 | `&'a T?` | `(&'a T)?` | `?&'a T` |
| 两层可空 | `(T?)?` | `(T?)?` | `?(?T)` |
| 可空数组 / 元素可空数组 | `[T; N]?` / `[T?; N]` | `[T; N]?` / `[T?; N]` | `?[T; N]` / `[?T; N]` |
| 可选切片窗口 / 元素可空窗口 | `&[T]?` / `&[T?]` | `(&[T])?` / `&[T?]` | `?&[T]` / `&[?T]` |
| 可空元组 / 可空元组元素 | `(X, Y)?` / `(X?, Y)` | `(X, Y)?` / `(X?, Y)` | `?(X, Y)` / `(?X, Y)` |
| 可空容器 / 容器中可空元素 | `Box<T>?` / `Box<T?>` | `Box<T>?` / `Box<T?>` | `?Box<T>` / `Box<?T>` |
| 可空函数值 / 返回可空 | `(fn() -> T)?` / `fn() -> T?` | `(fn() -> T)?` / `fn() -> T?` | `?(fn() -> T)` / `fn() -> ?T` |
| 可空调用能力 / 返回可空 | `(Fn() -> T)?` / `Fn() -> T?` | `(Fn() -> T)?` / `Fn() -> T?` | `?(Fn() -> T)` / `Fn() -> ?T` |
| 可空错误联合 / 成功值可空 | `(E!T)?` / `E!T?` | `(E!T)?` / `E!T?` | `?(E!T)` / `E!?T` |
| 可空错误侧 | `(E?)!T` | `(E?)!T` | `(?E)!T` |

最后一行仅说明类型树，错误侧是否可用还需类型规则。C 实验将 `?E!T` 解析为 `(?E)!T`；这是一项明确的候选优先级，不从 Zig 的作者动机推导，也不能借此前缀跨越 `!` 表达整体可空。普通联合也要区分成员可空与整体可空，三案采用同一语义层次比较。

可选借用与借用可空槽位在三案中都不可隐式互换。前者只在存在时提供对 T 的访问，后者才借用存储 Option 的槽位；丢弃借用句柄不等于有权清空原槽位。可选切片窗口与元素可空切片同样是不同层次。这些语义不因问号位置改变。

### 箭头、嵌套、泛型与打印

主线函数箭头取得完整返回 Type，对函数整体应用构造器需要分组。018 还实验过 `?fn() -> T`、`&fn() -> T` 的省括号形式；**这项函数类型文法调整不能作为前缀可空天然更短的证据。** 后续若调整，须在三案中分别检查 `fn/Fn/FnMut/FnOnce`、返回联合/错误联合、函数整体参与联合、闭包标注以及诊断打印，明确能否采用同一条规则。

两层 Optional 在语义上始终不同于一层。三案都要比较直接连续问号与显式分组的词法成本，不能先给 C 计入 `??T` 的紧凑性，却不考察后缀连续问号、表达式 `??`、两个传播操作之间的边界。主线与候选的实际接受性分别记录，不为比较偷偷开放新拼写。

泛型替换作用于 AST，不拼接文本。类型打印必须可重新解析到同一 AST，覆盖借用、箭头、联合、错误联合、嵌套 Option 与泛型实参；三案都不能依期望类型猜测结合。当前格式器主要正规化 token 间的空白，不能把现有格式测试说成完整类型打印往返验证。

## 必须共同比较的表达式合同

后文用 `Option<T>`、`Error<E, T>`、`None`、`Some(v)` 表示语义层次与代数状态，不确定 ZIL 的最终构造器或类型拼写。以下表达式功能都是三案共享的设计维度，**不因选择任一可空类型写法而自动实现或冻结**。

| 场景 | 同一矩阵必须回答的问题 |
|---|---|
| 错误传播 `x?` | 当前用于 `E!T`；与借用、成员、下标、调用及连续传播如何分组，诊断能否直接说明实际类型 |
| Option 传播 | 是否也用 `x?` 将无值传播到返回出口；若共用，依据操作数与返回类型明确区分，错误与无值是否允许跨层转换 |
| 判空 / `if let` / `match` | 解开后得到值还是借用，是否移动；显式绑定与稳定值收窄各需要多少语法与心智切换 |
| `?.` 成员、索引、调用 | `?.name`、`?.[i]`、`?.(args)` 是否采用共同入口；链分组、跳过的求值范围与错误传播位置如何统一 |
| `??` 默认值 | 是否只解一层、RHS 是否惰性、结合性及与布尔/管道的优先级是否易读 |
| `??=` / 链赋值 | place 求值次数、RHS 跳过、目标预约及权限是否明确；读取链不能自动成为可赋值位置 |
| 嵌套与泛型 | 两层 Option 的三种状态如何保留；泛型 T 与实例 T=`Option<U>` 的同形表达式是否稳定 |
| 词法与错误恢复 | `?.`、`??`、`??=`、`?[`、`?(`、连续 `?`、注释与换行能否避免意外解释成其他操作 |

`?` 兼作 Option 传播和错误传播，可能让消解方式更统一，也会增加出口和嵌套类型的判断负担；二者分开则相反。该取舍必须同三个类型候选一起放入完整程序，不能只保留“前缀可空 + 既有错误传播”的一个组合再宣布全场景最优。主线目前没有因本讨论新增 Option 空值传播。

### 链求值、副作用与分组

共同待验合同可以先采用一个入口族：`?.name`、`?.[index]`、`?.(args)`，再与直接 `?[`、`?(` 的必要性对照。基值只求值一次；无值时跳过连续链中尚未执行的字段、下标、实参、展开和调用，已发生的副作用不回滚。括号结束连续链的范围，括号外按实际产出类型继续检查。链处理无值，不吞掉错误、越界或权限违规。

例如 `callback?.(...prepare())` 必须测试空回调是否跳过 `prepare()`，以及是否错误地提前移动参数；存在分支沿用普通调用的移动、借入和失败清理。`obj?.method(args)` 检查接收者，`obj.handler?.(args)` 检查 callable，继续使用 ZIL 的 self 和调用能力规则，不导入 JS 的动态 this。

这些合同要由真实 CFG 与状态序列核验。能够解析链，不能证明调用、副作用、FnOnce 或借用生命周期正确；也不能隐式 clone、装箱或延长借入期来弥补实现。

### 链终点保留还是吸收 Option：仍待决定

设 `a: Option<A>`，`A.b: Option<B>`：

| 输入 | 保留终点层，结果 `Option<Option<B>>` | 吸收已有层，结果 `Option<B>` |
|---|---|---|
| `a = None` | `None` | `None` |
| `a = Some(A { b = None })` | `Some(None)` | `None` |
| `a = Some(A { b = Some(v) })` | `Some(Some(v))` | `Some(v)` |

保留层次能表达“没有对象”和“对象存在但字段没有值”；吸收层次更方便普通取值，但会丢失该区别。Swift 采用不因链给已有 Optional 结果再加一层的规则；JS 的 nullish 行为没有提供 ZIL 的显式三态类型，不能直接搬作答案。两种链规则都不推出 `Option<Option<T>> = Option<T>`。

泛型是关键反例：`Box<T>.value: T`，从 `Option<Box<T>>` 取 value 的函数若返回 `Option<T>`，代入 T=`Option<U>` 后自然得到两层。若具体类型的链会吸收已有层，具体 `Option<Box<Option<U>>>` 的同形表达式可能只得到一层。需要明确选择保持替换稳定、接受抽象边界差异，还是引入可表达的类型归约；不能在单态化时偷偷更改函数签名。

保留方案还要区分“一条连续链增加一层”与“每个 `?.` 都加一层”：显式检查中间可空字段与保留终点的可空字段不是同一动作。共同样本须包含普通字段链、可空回调结果、泛型和具体实例、补丁三态、链后默认值；记录额外解构/flatten、误读和诊断成本后再选择。当前不定任何一案为链语义赢家。

### 错误与可空交错

`Error<E, Option<T>>` 与 `Option<Error<E, T>>` 必须区分。对应 A/B 的 `E!T?` 与 `(E!T)?`，以及 C 的 `E!?T` 与 `?(E!T)`；无值和错误不应因一个问号自动交换层次。

同一表达式样本至少比较 `a?.read()?`、`(a?.read())?` 和 `(load()?)?.field`。若链内 `?` 只在存在分支传播错误，第一种与先结束链再传播的第二种就有不同类型与出口要求；是否采用这种规则，需与 Option 传播方案一起决定。不能靠隐式 transpose 或期望类型猜测把它们做成相同操作。链方法成功值还可空时，继续纳入终点层次比较。

### 默认值、判空与权限

`??` 的共同候选是只解一层 Option，RHS 延迟计算普通 T；`Some(false)`、`Some(0)`、`Some("")` 不触发默认，`Some(None)` 解开后也不继续自动 flatten。右结合适合 `a: Option<T>`、`b: Option<T>`、`c: T` 的 `a ?? (b ?? c)`，但优先级及混写规则仍须用相同样本比较，不能因为参考 JS 的 `?.` 就自动采用全部相关运算规则。

样本应包括 `a ?? b + c`、`a ?? fallback |> render`、与 `&&`/`||` 混写及括号变体。`place ??= rhs` 还需检验接收者和索引只求值一次、已有值时跳过 RHS，以及重入/挂起后的目标预约；它不自动成为并发原子初始化或有值赋值表达式。

`if let`、`match` 的显式绑定适合作为可空消解的基本样本，再比较稳定值判空后的收窄简写。写入、可失效调用、重入和挂起后不能继续沿用旧事实；共享借用可空槽位即使判定存在，也不获得独占借用权限。三案都须让来源、借入期和失效事实进入核验；`?.`、`??` 与判空均不能制造权限。

## 官方资料支持的事实

### Zig 当前版本与表达式分工

2026-10-23核对官网稳定入口为 **0.17.0（2026-10-01）**。Zig并没有把类型与表达式都改成前缀问号：`?T`构造可空类型；`value orelse fallback`给默认值；`if (value) |payload|`在存在分支绑定；`value.?`断言解包，等价于`orelse unreachable`；`try value`和`value catch ...`处理错误联合。`.?`不是JS的`?.`，不会在空值处产生可空结果并跳过后续链。依据是[0.17.0参考](https://ziglang.org/documentation/0.17.0/#Operators)和[版本入口](https://ziglang.org/download/)，不是对设计者动机的推测。

表达式当然可以调整，但不能靠把所有操作改成`?expr`消除语义分支。`?load().field`若沿用常规后缀优先级，是先访问成员再处理结果；`(?load()).field`才是先处理结果再访问成员。让前者自动获得后者的含义，仍要增加特殊优先级或整段链的提升规则。断言、无值早返、跳过后续链、默认值又有不同出口和副作用合同，不能交给期望类型猜测。

按“类型与表达式组合的例外最少”这个目标，**下一次同语料比较优先验证B，再验证C**：B较好保持后缀局部组合方向，C较好保持类型构造按外到内读法。这个次序是设计判断，不是测量排名；主线A仍保留，且其短写优势不直接算为全场景一致性胜出。表达式以传播、链、默认和分支分别集中成少数固定规则，比强求同一个问号承担所有操作更清楚。两层Optional、泛型替换和错误/可空换层仍须用上文同一矩阵检验。

| 一手资料 | 可核对的事实及限制 |

| [Rust Option](https://doc.rust-lang.org/std/option/enum.Option.html) | `as_ref`、`flatten`、`transpose` 分别处理借用、嵌套层次和 Option/Result 换层，不能混为一个隐式操作 |

## 实验身份与下一步

018 候选提交 `bdc9872a388aa2f1c4b1e24f03b56bac6e4cd636` 的限定 `zil-syntax` 测试为 56 项通过，包括前缀 AST、后缀类型拒绝与表达式预留诊断。该成绩只说明这个实验的 parser 行为；**拒绝 `T?`、允许前缀类型以及新增 `E-PARSE-OPTIONAL-EXPR` 均未成为主线规则**，更不代表三个候选的共同用例已经验证或 Option 运行链路已完成。

实验指出了一个须共同处理的边界：`x?.field`、`x??` 不应意外被读成 Try 后接成员或两次 Try。实验采取明确拒绝并要求 `(x?).field`、`(x?)?` 分组；最终选择哪种表达式族时应重新共同核对，不把实验的拒绝集合直接当作终态规范。

下一步为三案填同一份真实小程序矩阵：引用/可空、数组切片、函数与闭包箭头、嵌套泛型、显式判空、Option/错误传播、链的展开与副作用、默认值、诊断与类型打印。先比较能否保持同一语义和清晰阅读，再用实际解构/分组次数、误读与反例辅助判断；无证据时保留待决，不根据已完成的实验投入选择赢家。

该候选比较不阻塞共享捕获、质量队列和现有源码到原生程序的贯通。后续 Option 实施先完成最小值构造、解构与类型检查，再补短路 CFG 和后端；`zil qc` 用状态序列和独立 oracle 检查跳过、副作用次数、惰性、嵌套状态、出口与清理。实施顺序不提前裁决问号位置。
