## 四、本轮闭包施工建议

### 1. 对用户的普通源面应当短

建议把以下形式作为人体工学目标，而不是要求用户写捕获协议元组：

```zil
let offset = 10
let add = move x => x + offset
let answer = add(32)

var count = 0
var increment = () => { count += 1 }
increment()
```

第二个例子需要真实独占借入；如果本轮 C1 只完成 move+Copy，第一个可以成为真实源码目标，第二个必须继续准确标注未实现。不能以“自动按值”让第二个假通过。

Fn 约束建议形如 `F: Fn(i32)->i32`；`fn(i32)->i32` 保留为无环境函数指针。两个签名在存储、调用与 ABI 上的区别可以由类型系统保持，而不是要求所有应用程序员学习 `(T,)` 作为单参数协议元组。

### 2. 首个真实切片可以小，但不能改变完整语义

建议 C1：明确 `move`、只捕获 Copy 标量、局部具体环境、直接调用且不逃逸、Fn 可重复；真实环境字段与入口、typed CFG 和独立 verifier 都必须有证据。保留基线的普通非 move 捕获 Unsupported，直到借入窗口与 Hold 可核验。

参数和返回推导应与该子集一起落地常见形状，不能只跑 `(x: i32) => ...` 然后说“已达到 Rust 级闭包体验”。没有唯一约束时允许精确报错；不应为通过调用点而重试不同捕获或签名。

至少应验证：创建时 snapshot、创建后外部改值、重复调用、嵌套词法绑定与遮蔽、错误 arity/type、捕获排序/唯一字段、伪造捕获类型或环境布局被 verifier 拒绝、未支持普通借入和逃逸不被默认放行。

### 3. 本轮应记录的新裁决

建议优先明确：裸单参箭头；闭包参数/返回推导；Fn 约束的调用式源面；是否加入闭包块尾表达式。冒号返回、`.<T>`、`.{}` 与匿名记录可保留当前方案或另行修订，但必须写清理由和当前唯一写法。

记录更新、`&T?`、函数指针/callable 形状有实际语义差异，应单列决定或具名后续任务。把这些遗漏只归类为“旧对话拿不到”已不适合本轮。
