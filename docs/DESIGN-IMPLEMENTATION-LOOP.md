## 本轮实际吸收的来源

用户提供的[《zil设计3》完整共享讨论](https://chatgpt.com/share/6adda0ce-582c-8320-84b2-b3364357c888)已取得并读取相关优化及0.3–0.6结论。公开用户/助手文字单独保留；浏览器启动数据不进入交付。实际复用 `zil-boundary-lab-0.6.0.zip`，SHA256 `c22948a96d9f9de4a615dcf3314f393a44a3066b2701b6a50fa5b3e15dc6572a`，没有重新编写同名求解器冒充旧实现。

Rust四目标同时成立、并至少取得一项实质突破，仍是合取要求。当前设计允许在证据支持时大幅改造，不把既有实现当作必须兼容的包袱；实际能力和已知反例仍须保存，不能因换设计丢失安全义务。

| 设计讨论中的问题 | 本轮生产反馈或落地 | 当前边界 |

| 同一选择位置关系不能退化为相同may-source集合 | 095从实际活窗冲突生成形参apart义务，并在调用处实例化；有序同源合法控制仍接受 | 更一般的selected-place相关性没有实现，当前来源并集保守拒绝仍存在 |
| must有效、may保留访问权限与清理债应分开 | 真实来源、loan活性与唯一责任各自重建；Desc ValueHold不创建loan；give参数是本地拥有载体 | 不能把其中任一集合替代另外两个，普通公开合同尚不完整 |
| 危险prefix、正常返回与返回后状态都重要 | 原Lab消融反例原样复现；生产接口区分实现hash，但尚未区分一般prefix/mayReturn | 禁止未经合同扩展就用contract-only相等替代实现依赖 |
| 重复调用应消费摘要，避免展开函数体 | 真实双调用DAG深度0–64的体访问已线性；生产已具有有限摘要和080依赖工作队列 | 不把旧Lab0.5弱基线问题重新宣传为本轮生产突破 |

## 两条线怎样同时推进

每轮只增加一个共同的“主张—义务—证据”记录，复用现有工单、规范提案与独审流程，不另设批准链。

1. 设计线明确所需观察和可反驳主张：是否保持接受集合、是否只换表示、是否改变消费者查询接口、完整成本边界是什么。
2. 施工线给出真实源正例和最近反例，并回送精确提交、Typed CFG、公开接口、诊断、机器表示和清理顺序。没有的能力明确标缺失，不把语法不支持当安全证据。
3. 同一反例在研究模型与生产中分别登记。原Lab的destroy不能偷换成生产WriteDesc；它们对责任与失效的影响不同。
4. 设计需要修改公开语义时，先更新主规范与schema，再并行展开前端/Analyze、独立Verify、Lower/机器消费者。Verify继续独立重建，不消费前端许可。
5. 性能候选先固定强基线、功能身份、预算、样本和停止条件，再使用短暂独占窗口；其他时间各工作树并行。NoGo留证据和补丁，生产恢复基线。

本轮实际已产生18份沿原0.6反馈模板填写的生产收据，以及schema17新增的源面/raw-wire/机器三层证据。研究093固定schema16；语言094–096固定schema17，不混合计数或重标旧测量。

同一对话和当前工程可以继续承接。独立分支、输出目录和明确计时窗口已经足以隔离研究与施工；目前没有为了研究另开对话的技术必要。

## 下一轮共同观察面

优先完善“普通函数的危险前缀、是否可能返回、返回后必要关系”与真实别名的对应，再判断能否按支持集局部查询。共享guard、控制PC、错误出口、递归以及SCC撤销都必须进入分解条件。公开合同的观察充分性应先得到反例检验，再尝试减少失效传播或联合状态物化。

语言侧下一组义务来自可保存的动态拥有存储：Package/闭包环境、普通错误载荷及替换如何持有和清理；一般元素容器还需要对齐、元素析构和部分初始化。字符串应明确UTF-8验证与索引单位。可以先设计这些合同并行准备测试，但不能把当前ByteBuffer自动当作这些能力已经完成。
