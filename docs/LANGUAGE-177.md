### State 真正持有动态子项

174 将 Store 的真实初始化前缀清理接入 Package 字段责任。取出字段后由新载体持有责任，旧字段槽失活；补回必须给出完整新值。替换先准备新容器，再清理旧前缀并提交，不能因准备失败丢失原有子项。父壳正常或错误退出时，只清理仍在场的字段。两个 Store 字段、零尺寸用户资源与较宽 Copy payload 都有独立原生输入；布局相同不等于资源责任可以合并。

作者 174 的限定 13 项和 50 次消费者执行、root 的非作者 4 组异形/反例分别保留。175 的作者 20 项与独审 4 组，以及 176 的作者 12 项与独审 7 组另列在各自收据中，不累加到上表完整 workspace 数字之外。

### 读窗口绑定实际 Store 和在场元素

175 的 `store_at` 对运行时索引执行 `0 <= index < len` 检查，再计算元素地址。已分配但不在初始化前缀中的 capacity 空位不会变成可读对象。共享窗口只能读取被允许的 Copy 投影，不能把一份 Managed 或完整 Package 头复制出去。

Analyze 与独立 Verify 分别重建实际来源和后续使用。仍被使用的窗口会阻止相关 reserve、push、pop、give、drop、父字段替换或父壳移动；跨函数及已准入闭包/Desc 合同的保守写效果也要参与；这不开放 Store 或整个元素窗口的捕获。两个参数名称不同不证明它们不相交。独审实际执行了 len 小于 capacity 的越界及负索引 trap，并保留 raw 与 Wire 两条篡改拒绝结果。

### 保存回调调用原环境

176 的字段借入直接定位实际具体闭包环境，FnMut 的多次调用不会每次从环境快照重新开始。即使闭包没有资源捕获，字段责任也不能因此重复发布。不同工厂即使产生相同机器布局或同一 ClosureId，也仍受源 opaque 身份约束。FnOnce 取走/调用后的再次消费拒绝；替换先保护新环境，再按既定顺序清旧捕获。

首片仍是单一 F、直接单一 Fn/FnMut/FnOnce bound 的有限拥有 State profile。签名中 F 只在一个输入形参出现，可用的 F、&F、&mut F、State<F> 入口仍受后续权限检查；“一次”不是只允许调用回调一次。两个 `State<F>` 参数、回调 State 数组、整个 State 捕获、一般 F 返回与未实现的借入环境逃逸不能因为单回调字段成功而自动开放。共享/可变权限降级与伪造字段索引都有独立 raw/Wire 检查。

## 177 实际组合程序

`examples/mainline/zui_language177/` 包含六个源文件，每个入口实际使用五个模块。`State<F>` 同时保存 Ticket、`Store<Item>`、实际 callback 以及 Copy 状态；Item 又保存用户资源和 ByteBuffer。普通具体 helper 负责容器构造、读取、增长，泛型 State helper 负责持有状态、同步调用与字段替换。

运行时输入选择 0、1、2、3 个旧子项，另有非法输入。两个入口覆盖：创建 State、多次回调、准备与替换子项、扩容失败保持，以及先取出 callback/Store 再提前退出。测试 oracle 预先计算声明序的 Drop 输出；分配探针拦截真实分配调用，逐点失败后核对旧内容/回调仍可用、实际成功分配数等于释放数、最终 live 为零。64 次执行中的 44 次探针全部平衡。4 次编译均实际完成一次独立 Verify。

泛型正文中的 Store 内建尚未统一开放，因此这里使用普通具体 `collection` helper；这是当前可用的语言路线。177 只将具体已声明的 `manages` 字段转交接入有限 State profile，不为无约束 T、借来的父壳、普通非 manages 字段或局部任意 give 赋予所有权权限。

### 本轮实际发现并修复的问题

组合输入先后暴露了具体字段 give、比较表达式错误地把 bool 结果 hint 传给返回 i32 的 helper，以及完整所有权赋值后 local 仍被标为 moved 的问题。修复保留字段级移动/补回状态，并只在 RHS 成功完成后恢复赋值目标的可用性。

非作者补充检查发现四个原本可用的普通泛型用法回归：带括号的 Copy 字段投影、固定 Package 数组元素的 Copy 字段读取、普通具体数组元素整取、`p = relay(p)`。原源码逐字保留，旧版本与非泛型对照也保留；最终四项均通过独立 Verify，RHS 重复消费 `p = choose(p, p)` 仍精确拒绝。

新的 11 项 root 组合回归，以及非作者 9 组新探针均通过。测试中曾误用两个 State<F> 参数和已取走字段后的整壳覆盖，分别违反现有 callable 输入 profile 与剩余资源责任；保留失败并修正测试预期，没有为通过夹具扩大生产权限。**部分 State 不能靠整壳赋值跳过旧字段清理**，该输入继续以 Analyze/SafeReject `store overwrites an unpaid resource` 拒绝。

完整 workspace 的首次运行保留三个精确预算夹具失败：新增 callback 字段检查确实增加了实际类型访问，夹具按真实新增访问数迁移 N/N−1，没有提高生产默认预算。第二次完整运行的两个旧 Verify 形状反例改为匹配现行更早且精确的拒绝原因，原畸形操作仍不被接受。构建缓存冲突、命令包名错误、早期消费者失败及独审夹具失败也保留原状态，不改写为 Pass。

## 目前可启动的 ZUI 范围与剩余前置

目前可开始同质完整 Item 批次、只读布局/绘制命令、普通 State 保存同步回调、分阶段更新的受限语言消费者。当前操作顺序应是 Store 窗口最后一次使用结束，调用 callback 并结束该借入，然后修改相关容器或 Copy 状态。这个起步范围不是完整组件树或长期外部事件系统的验收。

1. **泛型 Store 库协议**：让泛型正文中的构造上下文、原语、give 与失败传播有一致的实际约束，减少当前具体 helper 的分层负担。
2. **callback 的实际字段来源精度**：目前 op87 贷款保守覆盖父 local，同父壳的独立 Store 字段或 Copy 写入可能仍被拒绝；必须先独立证明实际不相交，再放宽。
3. **受限独占元素窗口**：当前 Store 窗口只读；布局/交互标记需要在运行时索引处更新 Copy 字段。Managed 字段取出、任意孔洞与窗口逃逸另立合同。
4. **跨目标和外部保留回调生命周期**：当前新 Store profile 仅支持经核验的 Linux x64 LLVM；其他 target 在独立 Verify 明确 Unsupported。Win64 ABI、分配失败与清理仍需实现并实际验证。OS 保留 callback 还需要注册失败回滚、停止接收、注销/排空、重入及最后执行者结束后的释放协议。Wine 结果不能称为原生 Windows。
5. **其余完整语言义务**：原 159 的直接资源数组 `[R; 2] = [R { .. }]` 仍因期望 Desc(R)、实际 Managed(R) 在 Types 拒绝；`E!ByteBuffer contract { result(give) }` 的 ByteBuffer 位于成功结果侧，这个直接拥有错误联合返回也仍拒绝；递归/异构拥有结构、一般借入逃逸、混合捕获效果、字符串不变量、并发/挂起/取消等未完成。
