# 080：让资源效果沿真正的依赖边传播

076 的阶段通过说明实验、对照与归档达到约定要求，生产准入仍是 NoGo。其 88.8 倍
属于完整有限关系查询的 direct 对研究 BDD 对照；生产编译器没有该 BDD 可直接替换。
080 从当前生产成本重新寻找落点：资源写效果变化时，只重新求解实际消费它的函数。

## 改了什么

Analyze 和 Verify 的资源模块都需要推导“此函数可能写入哪些输入/借入捕获”。此前
每轮检查全部函数，直至无人改变。新实现分别从真实调用指令构造反向依赖表；所有函数
先执行一次，有新效果时通知其消费者。最终检查仍遍历全部函数，不把暂时为空的摘要
当成安全事实。函数内的来源、责任、future-Desc、Package views、失败与清理规则未改。

依赖边覆盖普通调用、局部/SSA/借入 Address 的五种闭包调用。公开 helper 的消费者
读取已核公开合同，故不依赖它的私有摘要；依赖选择严格跟随各阶段本身的实际读点。
Analyze 的图、FIFO 队列和写效果集合不传给 Verify；Verify 自己构图并分批传播。

这是既有单调数据流工作队列的应用，图思想体现在精确依赖边与局部变化传播。它不改变
资源状态抽象、不引入联合状态枚举、不消除复杂程序的所有最坏情况，也不自称新图定理。
物理局部相互作用的直觉仍适合提出候选，但进入生产需要实际成本与完整检查证据。

## 为什么等价

每个摘要来自固定输入下的单调转移，范围是有限的输入/捕获索引。旧轮扫和新队列都从
空集合开始，只取并集。新队列最初覆盖全部函数；任一被消费的摘要增长都会使消费者
再执行，故队列耗尽时没有遗漏待传播依赖。各次推导不超出旧方程组的最小不动点，终态
也满足全部方程，因此两者终态相同。最后完整 validate 使用该终态，并保留原函数顺序。

证明义务集中在“依赖图不能漏实际读边”。测试保留仅测试编译的旧轮扫作为调度对照，
分别比较完整效果行与每函数最终诊断；独立审核还应检查所有摘要读取点。公开 IR 和
Wire 检查仍由原 Verify 重建。测试中的枚举不是全语言安全证明。

## 真实成本和预算

构图、表/队列、每条通知及最终释放均计入新算法工作预算；删除的整函数重算不再收费。
默认额度不改。工作 N 是确定性收费模型，不是 CPU 指令数量。新的队列建立会给小例
增加成本，不能只报告长链收益；无资源/无拥有闭包的既有早返回不变。当前候选未加
根据测量结果选择的尺寸回退，不通过丢结果或省 Verify 获益。

冻结执行基线为 draft16/schema13，语言主线的后续 schema 单独集成核验。实验目录保存
基线与候选精确提交、同一个 runner、完整源码/二进制/输入摘要、全部命令和逐请求结果。
正式性能采样须由 root 协调独占，准备阶段的计时不升级成性能证据。

```sh
python3 tools/research/080/run.py prepare --repo . --candidate FULL_COMMIT --out NEW_DIRECTORY
python3 tools/research/080/run.py sample --out NEW_DIRECTORY --window ROOT_WINDOW_ID
```

14 个预登记语料族共 17 个模式单元：纯标量、未使用资源声明、短/长正反链、星形、
不连通分量、递归环、借入闭包、公开 helper，以及实际 owned_component 三入口。
前三个实际组件入口同时测 Verify 和 Build。每进程执行 cold、unchanged、private_edit、
public_edit 四个完整 compile_path 请求；编辑分别追加未调用私有和公开函数，模拟的
只是这一明确编辑形状。相同会话中的 Verify 每次独立运行，不能省略为缓存命中。

功能准备打开完整阶段产物并逐字 hash 对照，Build 再核对真实输出/退出码。采样不写
未请求的阶段 dumps，记录完整 API 时间、编译器报告时间和进程 wall，保留 Linux
VmHWM。API 内含文件读取/发现、失效/指纹、实际求解/检查和 Build 外部编译链接；
进程 wall 另含 runner 的保存/输出/销毁。VmHWM 是同进程四个场景的总高水位，不能
称为某阶段独占内存。每组一轮预热和七轮保留，配对先后轮换，全部样本均保存。

## 与既有方法的关系

[Rust 查询文档](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html)
解释纯查询、显式依赖及重新验证带来的成本。本片只做单请求内的资源效果依赖调度，
没有实现跨会话 red-green；其失效边界自然为此次 Analyze/Verify 调用的结束。
[Polonius](https://rust-lang.github.io/polonius/)是关系式借用检查的参照，不替代 ZIL 的
责任/清理合同。

下一研究仍可独立比较按事件读写支持更新共享子态与条件分量切割。已有
[dtree 论文](https://arxiv.org/abs/2007.12174)研究部分重建/增量状态更新；080没有实现
该算法，也未借用其论文数字。任何新的联合关系候选仍须对强 dense-direct 基线核对
完整输出与全部构造/恢复成本，再判断它是否符合生产真正需要的查询接口。
