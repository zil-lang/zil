# CP04：O0 标准 mem2reg — NoGo

## 裁决

回退候选，恢复 CP02 的全部 crates。实际 LLVM 指令数下降没有转化为整体编译收益，且中、大规模程序的运行时间退化。既不保留默认 pass，也不把小样例运行加速单独拿作成功。候选 `527657a9256cfaae2babb88dc8a2e3f78f4d6092` 留在研究历史；其 crates 与真实构建/审核的 `701dd6c18020607a4d89d51239c9dba59ea90e33` 完全相同。

## 实际改动与测试

候选只把 O0 pass 改为 `default<O0>,function(mem2reg)`，O2 仍为 `default<O2>`；共享实际配方 accessor，并在对象缓存 namespace 显式纳入完整字符串。编译器/LLVM 身份、目标、codegen 级别、独立 Verify、前后 LLVM Verify、取消、错误传播和发布次序保持。

作者限定测试 8+4 项通过，包括 16 次真实构建、44 次执行；根独立影响闭包 27 项通过（llvm_api208 11、object_cache212 11、stage_timings 5）；非作者静审通过。测试覆盖循环合流、地址用途/重借用、资源清理与溢出 trap，均为有限行为证据。当前否决原因是性能，不把测试成功称为全语言证明。

同版本 opt 文本诊断（非生产路径）显示 tree1024x8 的 alloca/load/store 从 10,246/19,465/19,464 降至 0/0/0，增加 3 个 PHI，总 LLVM 指令从 242,774 降至 193,602；retained 从 27 个 alloca 降至 6 个，保留有地址用途的聚合 slot。四次前后 Verify 均成功。该结果不能替代机器码与运行测量。

## 解释边界与后续

机器可执行体积在中、大样例增加，LLVM IR 变少并不意味着 O0 指令选择/寄存器分配会产出更小、更快的机器码。当前没有硬件计数器归因，不能将退化断言为 cache miss、分支预测或某个具体 LLVM pass 的问题。

既有正式记录中的无条件 LLVM Receipt 还提供了成本解释。对 tree1024x8 沿同一配对区块规则聚合：optimize 从 13.31ms 增至 98.71ms，object emit 从 898.85ms 降至 887.14ms；先逐条相加再聚合的 optimize+emit 增加 71.21ms。此次提升成本未被发射节省覆盖。它是实现作者对现成记录的诊断，不冒充非作者审核；分别聚合的中位数不严格可加，也不能解释原生运行退化。

非作者独立复算已完成：compile 使用 Decimal 45 位并穷举 27 个配对重采样，240 行/768 次原生 oracle 及全部日志摘要通过；runtime 使用 Decimal 50 位并精确枚举 3,125 个区块重采样，3,446 项核对、1,636 个文件哈希核验通过。双方未调用原聚合实现。另核对 CP04 的 A 臂与 CP01 的 A 臂，15 个语料/快照格的完整原生程序哈希相同，说明所测产物未因关闭的 tracing 而改变；这不证明 tracing 的编译开销为零。

原始计划、记录、日志与完整输入已无损归档至 `evidence/research/compile-performance/cp04/raw-evidence.tar.xz`，逐一解压核对 12,032 个文件。独立复算单独附加，不覆写原 summary 中生成时的 `independent_review: NotRun`。直接 SSA lowering 或其他指令选择路线必须先处理本次机器码质量风险，再新开候选和运行质量窗口；不能把本轮 mem2reg 负结果外推成 SSA 原则本身无效。
