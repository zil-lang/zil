# ZIL 编译速度审计与突破路线

日期：2026-10-31。范围：当前 main、GitHub 编译专项分支、最小机制复现及外部一手资料。本文是研究评估，不是正式产品验收；没有修改项目源码、合并或推送分支。

## 判断

有明确的结构性性能问题，尤其在增量链路。当前不少缓存是在已经遍历、展开、复制、哈希整个项目之后才决定复用；输入和结果的边界也偏大，因此“命中很多函数/对象”和“少做很多完整工作”并不等价。现有负结果与这一解释一致。

最有希望的方向是把一次局部编辑的真实语义影响，贯通为从前端查询、不可变 IR 到对象生成的工作边界，同时缩减每次完整请求仍必需的核验和链接成本。不能承诺仅靠这条路线必然打败 Rust；它是当前证据最充分、值得优先投入的假设。

这些原则并非项目规范缺失：`_zil_design.md` 19.1–19.4 已写明细粒度查询、共享核验输入、稳定身份和动作键分离。主要缺口是生产数据流尚未完成这些边界，已有局部候选也未形成完整纵向闭环。

## 2. 本次新复现的机制问题

### 2.1 默认缓存存在容量断崖

`CompilationSession::default()` 容量 32；请求开始时，若 raw 快照数超限就 `clear()` 整个数据库和快照表。

本次在 main 与 compile7 分别构建/链接限定探针，用公开的 `CompilationSession::compile_project` 请求到 Verify（模块数包含 root）：

| 输入 | 首次后缓存查询数 | 完全不变的下一请求复用查询数 |
|---|---:|---:|
| 28 模块 | 32 | 32 |
| 29 模块 | 33 | 0 |
| 40 模块 | 44 | 0 |

全部请求成功，且每次 `verification_runs=1`。这不是微小的淘汰效率差异：刚超容量后，整个项目每次都会清空缓存。应把仍活跃的当前依赖图和历史版本分开，以字节预算、有界保留和具体淘汰代替清空。只把 32 改成大数仍未解决生命周期及内存边界。

文件路径适配器在 clear 前可能已经借到 Parse Arc。因此文件入口 query_events 全部 Executed 不能直接解释成所有底层解析都重做；本表使用明确的内存项目入口。另测 29 模块真实 import 项目也观察到后续语义阶段全重算。

源码：main `crates/zil-driver/src/session.rs:77`、`project.rs:63`；compile7 同样保留该行为。证据：`incremental_probe_{main,compile7}.jsonl`、同名 `_summary.json`、`check_incremental_probe.py`。

### 2.2 预算余额混入缓存身份，制造无关失效

容量设为 1000，4 模块，保证不触发上述问题：

- 首模块私有体只改一个等 token 数常量：另外 3 个 Parse 复用，Expand/CT/Types/Analyze 全部重做。
- 首模块私有体改为等值但增加 token 的表达式：另外 3 个未修改模块的 Parse 也失效。

两版均复现，所有请求仍完成独立 Verify。CP33 正是针对第二种问题的已有候选，不能把它包装成本次新发明。

应分离“语义输入身份”与“本次额度是否足够”。缓存同时保留实际逻辑费用收据，命中时继续扣费；不足时走能保持首错、Span、部分使用量的原路径。推广到 CT/Types 时不能只存总费用：多维额度、失败位置、顺序和峰值可能需要前缀/组合摘要。先证明可组合性，再扩大复用范围。

### 2.3 未用外部声明污染所有对象缓存键

本次用 main 已构建 debug CLI、4 模块、4 CGU 做行为控制：

| 操作 | 对象命中 | 程序输出 |
|---|---:|---|
| 首次 | 0/4 | 42 |
| 完全不变 | 4/4 | 42 |
| c 函数 return 12 改 13 | 3/4 | 43 |
| 恢复 | 4/4 | 42 |
| 在末模块增加完全未调用的 extern 声明 | 0/4 | 42 |

原函数 ID 与正文不变；LLVM 文本差异只有授权指纹注释和该条 declare。非定义项目进入全局 prelude，每个 CGU 复制它，对象键再哈希全部 items。compile7 源码仍有相同机制。本次没有将 debug 运行时间作为性能数据。

应从结构化引用图为每个 CGU 构造实际需要的声明/类型闭包，覆盖调用、取地址、全局、函数表、Drop、闭包 helper、ABI 与布局依赖。无关 extern/类型不应进入每个动作键。签名相同不代表所有机器依赖相同，不能靠任意过滤声明来追求命中。

证据：`backend-probe/`，详细源码位置与重放步骤见 `backend-audit.md`。

## 3. 更深的架构原因

### 3.1 目前主要仍是整项目阶段缓存

compile7 `project.rs:200–209` 用完整项目指纹构造后续阶段身份；`session.rs:195–210` 的实际依赖统一观察 PrivateImplementation。项目图大体仍是多个 Parse → 一个 Expand → 一个 CT → 一个 Types → 一个 Analyze。

拥有 Semantic/ABI/Private 枚举不等于调用者已经按这些结果面订阅依赖。CP32 的模块 memo 仍保存完整 CoreModule 和全局环境；它避开了部分 Builder 工作，却继续支付周围的整图构造、匹配和后续工作。

修复目标应是可运行的查询边界：`Body(def)`、`Signature(def)`、`Layout(type,target)`、`Effects(def)`、`Lookup(namespace,name)`、`CtValue(input)`、`Instance(args)`。只有真正读到某一结果面的消费者才依赖它。重新计算但结果相同，应停止向下传播。

必须记录“名字不存在”的负查询；否则新增声明会改变绑定，而缓存看不见。整体枚举一个 namespace 的消费者应依赖集合本身。effect 删除、符号删除和递归边变化需要 SCC 重算或可撤回事实，不能把旧事实与新事实永远求并集。

### 3.2 稳定身份、源位置和语义值尚未充分分离

当前局部编号和遍历顺序参与很多身份。插入声明可能改变后续函数编号和机器符号。按旧 Span 保存完整 IR 又会使纯位置移动污染语义复用。

应采用稳定声明/实例身份，保留局部紧凑 ID 作数组索引；源码锚点和诊断位置单独映射到当前快照。声明身份应包含绑定、名义来源、卫生/生成来源；泛型实例另含真实类型/常量/选择，不能按同布局合并。匿名声明无法可靠匹配时保守失效。

这也是减少冷构建成本的基础：不可变分块 IR、类型/符号驻留、按需投影，可避免反复深复制大结构。跨请求 arena 必须能回收旧 epoch，不能用无限驻留换“快”。

### 3.3 对象命中发生得太晚

主汇总路径仍先做 Verify、LIR 构造/复制、绑定检查、机器 IR 重建、LLVM 诊断文本渲染和分区，之后才知道对象可以复用。随后仍调用链接器。命中只省了后端的一部分。

CP34 已做流式指纹，CP35 已做共享 Verify 输入；应完成其完整成本与内存验证。但前者主要减少临时缓冲，不自动减少哈希次数，后者减少复制，不自动让核验只看变化部分。

真正需要的是：在当前独立核验成立后，由已验证的依赖关系证明某个单元的 lowering/机器输入未变，尽量在重新构造整个机器模块前复用工作产物；链接另有覆盖对象内容和顺序、脚本/库/启动对象、工具链与选项的完整键。闭包不完整时必须继续正常链接。

### 3.4 完整 Verify 给增量速度设了下界

若每个请求仍独立扫描大小为 N 的完整输入，其他阶段都精确增量后，完整请求仍有至少 Ω(N) 的这部分成本。不能同时保留这项实现方式，又承诺全请求 O(变化量)。

第一步保持当前信任边界：共享不可变输入，减少重复编码，改进局部检查器，让完整 Verify 的线性扫描便宜。第二步是独立研究归纳证书：候选给出块/函数/SCC 不变量，检查器独立核入口、逐边闭合、安全前提、调用合同、错误与清理路径，尽量用检查代替重复求解。规范 19.2 已允许研究这条路线。

完整读取证书仍可能线性；若要进一步只核变化的证明片段，就必须明确可信常驻状态、缓存证明、依赖完备性及当前请求授权组合的契约。它是架构研究，不能偷偷用哈希相同跳过独立安全核。

已有产品配置要求 Verify 前端占比不超过 25%、证书不超过 Typed IR 的 2 倍，禁止关 Verify 过门。证书构造、存储、读取、校验都应计入总成本。

## 4. 推荐的研发顺序

### 第一优先：一个贯穿实际编辑流程的精确增量闭环

先覆盖真实模块中的普通函数体编辑，保留其它语言能力的正确整批回退。贯通稳定身份、signature/body/effect 分面、真实依赖读取、不可变函数 IR 与 CGU 工作产物。单做数据库调度改造或在现有全项目函数外再套 memo，预期收益有限。

复用同一编译服务入口，明确常驻/一次性 CLI 两类工作流。主干每次 CLI 创建 Session；研究线 CP12 已有完整输入相同的跨进程 checkpoint，但编辑后仍失效。可采用显式常驻服务，或可校验的持久细粒度缓存；二者有不同冷启动、存储和内存成本，不应混计。

第一批成功条件应是工作量：保持当前 Verify，每次只改一个叶子函数时，Types/Analyze/Lower/Codegen 实际处理的函数数不会随着无关模块数一起增长；无关声明不改其他动作键；公开效果/布局变化则确实传播到应受影响者。总耗时仍可能受到完整核验和链接限制，应另外报告。

### 第二优先：按证据消除高占比的固定成本

完成 CP34/35 独立 A/B，补实际分配字节、遍历节点、哈希字节、复制字节。比较正常无转储构建与诊断转储的费用，研究诊断文本按需/延迟生成。若固定文本文件本身是当前可观察产物，先明确兼容方式，不能在基准中偷偷关闭必需输出。

修复容量断崖、预算非语义失效、CGU 全局 prelude 污染。这些是确定性工作量问题，先用小控制证明机制，再进入正式耗时窗口。

### 第三优先：按剩余剖面选择一次高风险突破

| 方向 | 何时值得做 | 最大风险 |
|---|---|---|
| 归纳证书/分块独立 Verify | 核验占前端显著比例且重复求解是主成本 | 证书比重算更大/更慢，依赖或清理边漏核 |
| 持久函数代码与增量链接 | 完整前端已快、链接/重发射成为编辑主成本 | 重定位、地址稳定、代码增长、调试和异常信息复杂 |
| Cranelift 开发后端 | O0 后端占比足以偿还维护成本 | 运行质量/ABI/平台能力和新后端维护成本 |
| effect/借用分析的增量 SCC / 差分数据流 | 真实大程序在固定点求解上热点明确 | 事实删除错误、索引/RSS超过省下的工作 |
| 泛型实例共享/形状特化 | 重复实例是已测主要成本 | 相同布局不等于相同Drop/名义/错误语义；擦除可能损伤运行性能 |

Cranelift 可以作为可选开发配置研究，LLVM 仍承担优化输出；它不会自动让四目标同时成立。若前端和完整 Verify 占大头，更换后端也不会救整体增量。差分数据流应与简单 dirty-SCC 重算比较，避免再次只优化一个求解器而端到端没有收益。

## 5. 最便宜的证伪实验

1. **规模斜率**：固定一个函数编辑、固定调用影响范围，逐渐增加无关模块/函数；分别记录 Parse、Types、Analyze、Verify、Lower、hash、codegen、link 的工作量与耗时。不是先跑数千次完整窗口，而是先证明重做范围。
2. **失效矩阵**：同 token 私有编辑、增 token 私有编辑、只改位置、插入未用函数/extern/类型、公开签名、布局、effect、CT 输入、内联/泛型正文、负名字查找、删除/恢复、递归 SCC、A→B→A。按真实消费关系检查应变和不应变者。
3. **当前请求正确性**：每次与 fresh 编译比较接受/拒绝、诊断首错与当前 Span；正确预算 N/N−1、失败/取消不污染下一请求；补原生语义/清理对照。命中率本身不能替代这些。
4. **端到端收益**：工作量控制通过后，再冻结源码和同机完整计时。分开 cold check、cold build、unchanged、private/public edit、IDE/daemon 与一次性 CLI；保留全部输出、p95、峰值和长期保留内存。
5. **补真实复杂程序**：保留原冻结权重，另外增加有 CT、泛型、资源、闭包和布局变化的消费者；不靠改变样本权重掩盖不利项。Rust Cargo no-op、直接 rustc、常驻前端也是不同接口，分别比较。

既有产品目标保持：cold check、cold debug build、private edit 中位数相对 Rust ≤1.0；编译突破候选 cold check 或 private edit ≤0.8。需要重复成立且无结构性退步。没有证据支持现在承诺 2×、10×。

## 6. 外部实践与研究的具体价值

- [Rust 增量查询](https://github.com/rust-lang/rustc-dev-guide/blob/69e3b706eac15d804c75ce6558cc8355aac4e3f5/src/queries/incremental-compilation-in-detail.md)：结果等值截止传播，稳定 DefPath 身份；官方特别指出 stable fingerprint 也很昂贵，大结果的 no_hash 与小投影查询可避免双重哈希。对 ZIL 的关键是把大对象复用变成小语义结果依赖。
- [Zig InternPool](https://github.com/ziglang/zig/blob/738d2be9d6b6ef3ff3559130c05159ef53336224/src/InternPool.zig#L836) 和 [Zcu](https://github.com/ziglang/zig/blob/738d2be9d6b6ef3ff3559130c05159ef53336224/src/Zcu.zig#L250)：区分源码、类型、值、namespace 与单个 namespace_name；区分可能过时与确认过时。值得学习实际依赖边界，不能简单照搬其语言和核验前提。
- [Build Systems à la Carte](https://doi.org/10.1145/3236774)：把调度和重建判断分开；正确的缓存系统也可能做很多不必要工作。这里的 verifying trace 是构建输入校验，不等于 ZIL 安全 Verify。
- [Adapton / Incremental Computation with Names](https://arxiv.org/abs/1503.07792)：稳定命名、按需求值适合思考跨编辑身份；[Salsa](https://github.com/salsa-rs/salsa/blob/d30612afc4237f2b0f1d3e132ad9bc27fe48b03d/README.md) 可承担查询基础设施，但不能替项目设计语义边界或预算收据。
- [rustc_codegen_cranelift](https://github.com/rust-lang/rustc_codegen_cranelift/blob/74bc4c2cc696bbb7499bb6104e872314d590a8ed/Readme.md) 提供开发构建快后端的现实方向；[Differential Dataflow](https://github.com/TimelyDataflow/differential-dataflow/blob/aa8745f93ea8abe131104fc7885ba4fd47e63902/README.md) 提供有增删事实的递归增量方向。均未在本项目验证收益，不套用外部倍数。

外部固定源码、相关行号与适用限制详见 `external-notes.md`。
