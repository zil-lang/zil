# draft17：从局部传播收益走向完整编译成本与 ZUI

核查日期：**2026-10-25 UTC**。源码阅读基点：`dfa565be7fe163393e3e59835037ce2d3277ad22`。
本文只记录架构判断和下一实验设计，没有修改语言规范、公共接口、产品门或生产代码，也没有新增性能测量。
后续三个研究项均为假设。正式集成与完整语言状态以主树工单及当轮验收收据为准，不能用本文覆盖它们。

## 1. 当前结论：值得继续，但交付中心应转向 ZUI 的真实前置

**继续 ZIL 有工程和研究价值；现有证据不足以证明它已整体优于 Rust。**
080 找到了真实生产瓶颈并形成可合入的优化，说明研究能够产出工程收益；它不是图切割复杂性突破。
076 则纠正了一个重要归因错误：直接有限状态转移胜过那一版研究 BDD 执行器，不能推出局部域、整态共享或图切割本身胜过强基线。
两者应同时保留：接受已证实的局部改进，继续检验尚未成立的结构假设。[L1][L2]

主线已有实际拥有资源、字段移出/补回、保存拥有环境的同步闭包以及本轮字节和有限同步借入 C 缓冲区能力。
它们可作为 UI 的资源和平台边界基础。当前固定数组不是动态容器，UTF-8 字节不是字符串类型，`noescape` 声明不是任意外部代码的安全证明。
窗口、字体、GPU、真正的回调关闭与后续并发/取消责任仍有缺口；不能把命令行事件演示当作对标 GPUI 的完成。[L3][L4]

建议下一阶段围绕“一种平台上的真实窗口、输入、状态更新、绘制和关闭”组织工作；语言功能按这个消费者暴露的缺口推进。
图研究继续占独立分支和有限研究资源，不成为窗口和库开发的前置。
这是投入顺序的建议，不是取消完整语言终态，也不增加发布审批或降低既有产品门。

080 的改变很具体：Analyze 和 Verify 各自构建资源效果的反向依赖图，摘要增长时重算消费者，最后仍完整检查全部函数。

冷场景是空会话、暖 OS 文件缓存；编辑场景只是追加未调用的私有/公开函数。

本轮 schema14 的功能集成不把这些旧输入、计时和限制改名为新结果。[L2]

## 3. Rust 编译成本：按工作负载定位，不能先认定借用检查最贵

官方指南提供 `-Z self-profile` 的查询级分析、原生 profiler 的函数级分析，以及 Cargo `--timings` 的 crate 图观察。
它在 rustc 自举这一特定场景说明大部分时间花在 LLVM；这不是所有 Rust 项目的通用比例。
本文未采样同能力的 Rust/ZIL 程序，因此不提供借用检查、类型推断或 LLVM 的统一百分比排名。[R1]

| 成本对象 | 已核实的机制 | 对 ZIL 的实际含义 |
|---|---|---|
| 类型检查与 trait 求解 | 约束、候选、关联类型、推断以及循环求解可能形成大量工作；新 solver 专门处理这类问题 [R6][R7] | ZIL 尚缺完整同类能力，少做工作不等于算法胜出；先测自己的受支持程序 |
| 借用检查 | MIR 上的初始化/移动数据流、区域约束、区域推断及最终访问检查共同构成工作 [R4] | 改一个集合传播可能有效，但不能假定它就是请求主耗时 |
| 泛型实例与机器后端 | 单态化生成所需具体实例，带来编译成本和代码体积；之后还有 LLVM 和链接 [R2] | 资源分析变快无法消除新增实例、优化与链接的费用 |
| 增量基础设施 | 依赖记录、指纹、缓存查找、持久化与重验证本身有费用 [R3] | 缓存命中率不能代替完整请求耗时；小输入可能不值得缓存 |
| crate 与构建调度 | 多个 crate 的执行和依赖形成构建关键路径；官方 perf 区分 fresh 与 incremental 配置 [R1][R8] | CPU 分项之和与并行构建墙钟时间分开记录；不能拿不同 profile 互比 |

### 3.1 red-green 的关键不是“只看文件是否变化”

Rust 查询系统把查询视为具有显式依赖的纯计算。输入变化后，某查询重新执行仍可能产生相同结果；red-green 据此停止无必要的下游失效传播。
跨进程还需保存依赖、比较结果身份、处理稳定标识与加载成本。这套思路比“一份源文件没改就整个复用”精细，也有额外成本。[R3]

ZIL 当前 `CompilationSession` 已保存不可变 `Arc` 原始快照，但 `query` 的源码注释明确：现有整模块 raw 查询保守观察完整 implementation identity；它没有声称跨模块私有正文的精细增量检查。
同会话每次请求仍新运行 Verify，缓存里没有 `VerifiedModule`。这些是现有边界，也是新研究的强基线，不能把已完成的 068 重复当作新突破。[L6]

### 3.2 Polonius 与新 solver 的 2026 状态应更新

Rust 官方 **2026-08-04** 公告宣布把 **Polonius Alpha** 放到 nightly 测试。它增加 lifetime outlives 关系的流敏感性；不能据此说旧 NLL 的所有数据流都不流敏感。
公告同时说明早期 Polonius 实现存在严重性能障碍，Alpha 仍不等同于旧实现全部接受能力，而且当前做相同或更多工作；它的主要新增价值是接受性，不是承诺编译提速。[R5]

官方 **2026-08-21** 公告宣布下一代 trait solver 在 nightly 默认启用。公告的 top 20,000 crates 比较中，大多数编译性能相近；少数 trait 密集项目有明显改善，也有回归治理工作。
因此，“采用最新 solver”既不保证普遍快，也不能只以旧 solver 的极端反例评价 Rust。[R6]

对 ZIL 更有用的具体借鉴是：canonicalization 可以保存和复用候选约束，减少重复求解；缓存仍需追踪实际依赖、循环上下文和可用递归深度。
Rust 的新 solver 文档特别说明递归预算会影响 ambiguity 结果，所以缓存不能忽略剩余深度。ZIL 的 ResourceLimit 语义不同，不能直接照搬其 ambiguity 规则。[R7]

这些是 2026-10-25 实际访问的一手资料；日期是公告发布日，不是本文替它认定的稳定版发布日期。
本次没有取得可核实的后续全局稳定化提交，因此仅报告已确认的 nightly 公告，**不把“计划年内稳定”写成“已稳定”**。
Polonius 也不替 ZIL 自动解决 Drop 顺序、Package 字段债务、拥有环境、失败清理与未来取消义务。

## 4. 物理类比应转成什么可检验对象

资源身份可类比有身份的粒子，责任位置可类比承载位置，move、borrow、drop、call 可类比局部事件。
有用的数学对象是 **事件读写支持、责任守恒、语义耦合超图和条件分隔信息**。这些类比用于提出算法假设，不构成证明或原创定理。

“某一瞬间只有一个拥有者”只是必要条件之一。来自哪个对象、是否初始化、是否仍活着、是否与可变访问冲突、错误路径怎样清理，都不能由拥有者计数替代。
静态源码位置也不是无界循环中所有动态资源实例的唯一身份。
流体平均值、连续松弛或随机近似若丢失身份和相关性，最多用于选择求解顺序、给出保守拒绝或触发完整回退，不能直接授予接受许可。[L1][L3]

把图切割理解为“寻找较小的语义耦合边界”仍值得研究。
关键宽度是约束/事件交互图中的分隔信息，不是 CFG 上切掉几条边，也不是把状态编号写得更短。
变量消元已有研究说明时间和空间随 induced width 增长；这提供边界分析工具，不提供 ZIL 的新复杂性结论。[R10]

## 5. 下一研究一：事件支持驱动的增量传播与子态更新

**假设。** 某些真实资源事件读取的状态和变化量远小于整个函数或联合状态。
若把计算绑定到经过核对的支持集，可以在 080 函数级工作队列之下减少函数内重算；对 076 完整关系模型，也可能减少整行复制/哈希。
两类接口必须分别评价，不能把研究表示收益直接记成生产收益。

### 候选与不变量

为事件 e 提取读取集合 R、写集合 W、故障依赖 F；缓存或更新只在 R∪F 和相关版本相同的条件下复用结果，W 外状态按原值保留。
来源相等、独占性、未来使用与清理约束若依赖其他坐标，也必须加入支持集；多边合法，漏边不合法。
不得只根据源码中显式出现的局部变量推断完整依赖。

生产试验先做一个窄候选：已有摘要增长时，传递新增效果位，并记录函数内哪些事件/块实际消费这些位；受影响块重新求解。
初始扫描和最后完整验证保留。只有完成整个请求内等价后，再讨论跨编辑保留状态。
删除调用或改变公开合同会让事实缩小，不能把“单请求中只增不减”的机制直接用于跨编辑删除；最初版本应重新构建受影响 SCC，而不是勉强保留旧正事实。

完整关系支线则比较“只更新 W 所在子树”的持久结构：共享未改子态，避免不必要的完整物化。
dtree 原论文确实研究部分重建和不完全具体化下的增量更新；它提供设计参照，论文速度不移用到 ZIL。
Differential dataflow 则说明迭代计算与输入变化是可分别建模的增量维度；本提案不声称已实现它的时间戳、撤销或执行系统。[R9][R11]

### 强基线与完整费用

生产基线必须是 **已合入 080 的完整编译器**，并保留直接重算、小位集和朴素块队列控制；不能继续拿已淘汰的全模块轮扫当唯一对照。
完整关系基线必须包含 076 dense-direct、local-direct 和整态 intern，先在同一冻结语义下比较，迁移 schema14 另核接受性。

费用包括支持抽取、索引、脏集合、持久节点/引用、哈希碰撞比较、回收、失效和恢复、完整最终 Verify、输出与释放。
若完整接口需要写出 B 字节关系结果，时间至少要支付 Ω(B) 的输出工作；流式输出能降峰值驻留，不能消除写出 B 字节的成本。
生产查询只输出摘要/合法性时，必须按其实际输出规模计量，不能虚构完整关系展开费用。

### 反证输入与停止条件

短/长态、稀疏/稠密写、正反调用链、SCC、递归 helper、Package 视图、借入/拥有闭包、错误/abort、共享 guard、多源别名都要覆盖。
最近反例是：callee 新增一个写效果，间接描述或共享拥有环境消费了它，但事件支持表遗漏那条边；另一个是删除写效果后仍复用旧摘要。
完整效果与最终诊断必须和强基线相等，ResourceLimit 差异单独记账，并核对新费用的 N/N−1。

出现漏边或漏故障就立即否定该实现；若完整请求不改善、只少了局部计数，或短态/稠密态回归抵消真实工作负载收益，则停止推广。
允许事先约定、同样收费的结构回退，但不得按结果挑赢家后删去失败输入。

## 6. 下一研究二：保留共享条件的精确分解

**假设。** 一部分程序虽然拥有许多资源，但资源间只通过少量条件、描述来源或合同发生耦合。
对这些输入，按语义依赖超图分解后，内部求解规模可能小于单体联合关系。
这是三项里潜在结构收益最大、同时风险最高的一项，应先留在影子研究。

### 可接受的分隔条件

对某点的完整关系 R，将变量分为 A、B 与共享分隔信息 S，候选要保持

\[
R = \pi_{A,S}(R)\;\Join_S\;\pi_{B,S}(R).
\]

这里是集合关系的精确连接，不是概率独立的近似。
初始关系满足该式还不够；每个转移、分支、合流、调用和失败观察也必须保持分解，或扩充 S/合并分量。
推导分隔条件的步骤不能调用最终完整枚举再把枚举费用藏掉；影子阶段独立 oracle 做完整核对，生产化需要可局部检查的支持/分解证据。

最近反例仍是 `R={(0,0),(1,1)}`：分别保存两个边缘集合并做笛卡尔积，会多出 `(0,1)` 和 `(1,0)`。
拥有者计数、两个分量各自安全、CFG 切口很小都无法排除这个错误。
共享 guard、跨分量 Desc、最后使用、错误出口和清理次序必须成为分隔信息或阻止切割。

### 强基线、下界与成本

比较同合同 dense-direct、局部直接转移以及保留全部分隔条件的候选；增加无共享条件的可分离族、单 guard 高耦合族、长生存期跨区描述、宽分隔和循环族。
先比较小图全部关系，再扩大有明确 oracle 预算的输入；OracleResourceLimit 不是正确性 Pass。
保留生产当前保守核，只让影子候选输出结果与证据；本试验不暗改语言接受集合。

若分隔有 k 个变量、每个最多 d 个值，显式分隔表本身就可能有 d^k 项。
变量消元的已有 induced-width 结果提醒我们：局部切口可能把难度移入更大的中间因子，而非消除难度。[R10]
总费用包含建图、选序、分解验证、中间因子、条件连接、去重、全部正常/故障/abort/出口关系、canonical 输出及独立核对。
完整输出仍受 Ω(B) 下界约束；若未来消费者改为直接查询紧凑关系，必须另立接口实验，不能用不同输出合同赢旧基线。

任何虚假笛卡尔积、遗漏故障、错误清理次序都否定该候选。
若所需 S 接近完整状态、因子峰值超过单体、或完整展开/核对主导而看不到净改善，就保留负结果并停止该输入类的生产迁移。
找不到非平凡可核验分解，也应直接报告，不以“图已经被切开”判定成功。

## 7. 下一研究三：减少纵向重复表示，并精确化失效范围

**假设。** 一部分完整请求成本来自同一结构的重复复制、规范化、哈希、遍历和过宽失效，而不是推理本身。
用户提出的纵向视角很有价值；可验证的目标是具体重复工作，而不是消除阶段边界本身。

### 当前代码里可检查的两个起点

在本阅读基点的 [session.rs](../../crates/zil-driver/src/session.rs) 中，`RawSnapshot::digest` 对 Typed 快照用结构指纹，对其他快照仍构造完整 `Debug` 字符串后哈希。
`finish_typed` 在公共 `verify_module` 调用前克隆 TypedModule 和 CandidatePlan，以满足现有拥有型 API。
这是可定位的操作，不是本次测得的热点；没有 profile 之前不能给它们编造耗时占比。[L6]

068 已有 Arc 快照、请求身份与惰性产物输出，080 已有资源效果队列；新的对照必须包含它们。
先记录字符串构造字节、结构克隆字节、指纹遍历次数、分配和请求内存保留，再分别试验流式规范编码摘要、不可变共享输入及稳定子查询身份。
不要一次把表示、求解、缓存和诊断都重写，否则不能归因。

### 保留安全核与有效缓存键

共享内容限于不可变原始结构、稳定 ID 和可独立核对的格式事实。
读写支持、来源与依赖等派生事实可以作为候选，但 Verify 仍须从原始输入独立确认相关义务，不消费前端“已安全”的结论。
每个完整请求仍运行独立 Verify；不把旧 Verified 能力放进跨请求缓存。
若采用 Arc 借入，也必须保持核验后的不可变性，不能让原始持有者在核验后修改同一对象。

缓存身份要覆盖规则/schema、target/ABI、模块及公开合同、实际读取的私有实现、构建输入、相关限额与诊断位置。
正文编辑但接口不变，只能使真正仅消费接口的查询保持有效；读取正文进行求解、CT 或内联的消费者仍要失效。
规范编码相等、hash 命中或 noescape 声明都不授予权限。
循环、预算和取消路径必须纳入设计；Rust 新 solver 的缓存深度规则是反例参照，不是可直接复制的 ZIL 语义。[R3][R7]

### 强基线、输出下界与放弃条件

完整请求比较 cold、unchanged、修改被调用私有正文、修改公开合同、CT 依赖编辑、插入导致 ID 重排、跨模块同名项、schema/target/限额变化，以及取消后的恢复。
080 的“追加未调用函数”场景要保留，但不能代替这些更难的失效场景。
基线是相同功能/产物的 068+080 生产实现，同时设置只更换 digest、只减少 clone、只缩小依赖三个控制，以定位收益来源。

费用包含事实构造、预检、指纹、缓存写入/读取/驱逐、保持输入存活的峰值内存、失败清理、完整 Verify、最终产物和 session 销毁。
独立最终检查读取的必要输入规模，以及真实请求必须输出的接口/产物字节，仍构成不能凭共享删除的工作。
不能为了得到“跨阶段只算一次”而撤销独立安全检查。

最近反例是编辑公开 noescape、参数 mode 或隐藏捕获写效果后，旧候选仍命中；另一个是同结构但源位置变更后出现过期诊断。
任何过期权限、漏失效、取消残留或越限复用都否定候选。
如果只是把工作从 Analyze 移到索引构造，或保留大对象让内存显著上升而完整请求无收益，就不合入。

## 8. 三项研究的执行顺序和共同计量

建议生产研究先做 **第三项的窄 profile 和单因素候选**，因为它直接对应当前可读代码；第一项随后针对实际重复求解最多的事件；第二项保持独立高风险支线。
这个顺序可被 profile 推翻：若克隆/摘要成本很小，就立即转向实际热点，不为已经选好的方案寻找宣传数字。

每个候选应先固定语义和观察接口、强基线、输入族及失败条件，再运行功能等价与独占性能采样。
记录完整 API、完整进程 wall、CPU/分配与总峰值内存；涉及外部 clang 时，要另采集子进程或进程树内存，不能沿用 080 的父进程 VmHWM 解释成总值。
所有设置、样本、异常、超限、输出差异和负结果保留。工作预算是确定性限额，不是 CPU 指令或分配量。

研究报告应分别回答：算法内部是否少做工作、完整候选是否获益、真实请求是否获益、目标应用是否获益、是否已达到现有产品门。
前四项不是第五项的自动通过条件。正式产品裁决继续只引用 [product-gates.json](../../validation/product-gates.json)，本文不新增或改写数值门槛。

## 9. ZIL 相对 Rust：价值与机会成本

| 目标 | 当前可核实的 ZIL 价值 | 仍缺的比较证据与能力 |
|---|---|---|
| 安全 | 显式责任、Desc/Managed、字段清理与拥有环境路径已有独立 raw/wire 核验；本轮有限借入 C 缓冲区保留 unsafe 边界 [L3][L4] | 不等于完整语言安全证明，也不能据此宣称强于 Rust；动态容器、一般组合、并发和取消仍需真实闭包 |
| 运行与内存 | 现有有限例可内联承载资源/环境，无为这些能力隐式插入 Box/RC；有真实行为与布局记录 [L3] | 没有同语义 Rust 应用的完整运行时间、峰值内存与尾延迟优势；这些属性也不是 Rust 无法做到 |
| 表达与维护 | 责任/描述模型有机会减少 UI 资源、组件与保存回调的用户侧样板 [L3] | 需让同一应用接受同一轮需求变化，测代码改动、诊断和修复；不能用语法短或测试多代替 |
| 编译成本 | 080 的真实资源依赖链有净改善，068 的结构复用可作为后续基线 [L2][L6] | 未证明同能力 Rust 编译更快；Rust 本身也在持续优化增量、Polonius 与 solver [R3][R5][R6] |

**值得继续的差异化问题**是：ZIL 的责任/描述和清理合同能否使真实 UI 状态、拥有环境、失败与关闭更容易表达，并在合理完整成本下验证。
“重新造一门 Rust，却先省略 Rust 的大多数复杂能力”不是足够的产品优势。
若重点是尽早取得用户可用的 GPUI 级应用，用 Rust/GPUI 实现通常具有现成框架这一明显机会成本优势；这是基于当前 ZIL 缺口的投入判断，并非本文做过工期或性能实测。
GPUI 官方展示的是 Rust 的 GPU UI 框架和真实窗口、布局/文本 API；我们的对标必须最终触及这些行为，而非只比较资源语法。[R12]

### 下一阶段具体投入建议

1. **主线约 60%：可承载应用数据的最小完整路径。** 优先解决实际 ZUI 需要的拥有字节存储、借入视图、长度/容量、边界检查及失败/替换清理；先明确受支持的固定容量版本，再推进动态增长。UTF-8 有效性、文本边界与字节容器分别列清。不要先铺满一般 trait solver、高阶泛型或所有语言糖。
2. **平台与消费者约 25%：单平台、单窗口、同步拉取事件的真实闭环。** 输入改变 ZIL 状态，ZIL 生成绘制命令，呈现到真实窗口，最后关闭窗口及相关资源。可以先使用有界命令容量、有限文本和一个平台后端，但必须公开限额。平台 ABI 的 opaque handle、所有权和销毁义务需要明确合同；不得把指针转整数或隐藏全局表当作绕过当前 ABI 缺口的捷径。若使用显式可信适配层，应把其范围与 ZIL 实际承担的状态/责任清楚记录。
3. **研究约 15%：一个生产热点候选加一个受限结构实验。** 研究不阻塞上面两个轨道；有数据的局部改进按已有独审流程合入，无净收益及时归档。该比例只是下一阶段资源建议，不是性能门或新增授权流程。

最早的 ZUI 阶段终态应能演示并自动核对：创建窗口、输入一次和连续多次、组件状态更新、可观察绘制、创建中途失败、正常退出以及关闭后旧引用不可再使用。
如果现阶段只完成 headless 命令列表，它是中间产物，不能记作 GUI 终态；如果使用同步事件拉取，也不能声称支持任意 OS retained callback 或异步取消。
GPU、多平台、完整字体整形和通用异步可以后续推进，但要继续保留其终态责任单。

若经过两个明确的消费者切片仍无法形成可见窗口与数据/生命周期闭环，就应重新缩小语言扩展范围，把更多工作放到可复用库与平台边界。
若结构研究反复只在合成图胜出，则暂停该路线的生产投入，保留研究成果，把下一实验改为真实应用 profile 暴露的问题。
这个选择保留长期语言目标，同时让每轮施工更接近用户要运行的 ZUI。
