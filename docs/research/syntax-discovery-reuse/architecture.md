# 089 的图边界：语法值、资源资格与跨阶段共享

本研究处理真实编译依赖图上的两个重复来源；它不是最小割算法，也没有提出新的图论复杂性结论。原有完整联合责任关系研究和生产独立Verify不由本实验替代。

## 为什么可以拆这条边

有限输入的成功语法值由源字节、文件/模块/路径身份、冻结规则与属性上下文决定。请求token/node限额决定计算能否成功；在该输入的实际需求已经满足时，继续增减富余限额不会改变成功AST。但把预算直接从键中删掉并不正确：`parse_with_limits`是包含ResourceLimit的可观察函数，热缓存不能把原本失败的请求变成成功。

K的结构是保留这一资源依赖，但将它从“成功值身份”移到“本请求复用资格”。成功解析同时产生实际lexer token、parser node与属性work需求；只有当前限额满足该需求才可复用。深度始终精确匹配，其余旧键字段也保留。资格不足或未知时回原有限解析器，让旧路径决定失败阶段、位置及顺序。项目仍按含EOF的token数扣本请求额度，不把省去CPU时间当作免费逻辑步骤。

这是一项带资格的依赖分离。其价值需要从K/B的实际结果判断，不能从更多query命中推出总体更快。

## 为什么还需要纵向通道L

主线068已经让发现import时得到的不可变AST直接交给后面的Parse查询，消除了同一次请求内的第二次解析。跨请求仍有重复：发现器必须先解析才能知道import，后面的查询即使命中，也无法收回前面已经发生的工作。

L让发现器先以当前实际源字节和正确身份查找已发布成功AST。命中只共享不可变Arc，不共享Verify许可。仍重新读取文件和解析当前import路径，保持删除、歧义、根目录、别名、模块ID和取消检查。ArtifactPlan完成前不发布新raw；超过现有容量的缓存不提前用于发现阶段。

B/K/L/KL分别保留两项机制的控制。B和K的热发现仍实际调用parser；L和KL才可能让该次数降到零。L保留预算相关键，因此前序文件增token可以令后续文件重新解析；KL才尝试去掉这一联动。实际次数由单独构建中lexer/parser入口计数，不以调度事件代替。

## 可信边界

`ParseRequirements`字段私有，只有本进程syntax成功路径构造。更关键的是CompilationSession的raw与资格映射都不是公共写入口：调用者即使取得某输入的收据，也不能把另一个AST和该收据注入session。磁盘缓存仍只是待查验源字节；没有持久化或反序列化资格、AST或Verified对象。

资格不证明类型、借用、初始化、所有权、FFI合同或析构正确；每个完整成功请求仍执行独立Verify。RawSnapshot::Parse的原Debug字节保持，不把新增元数据偷偷算入语言值摘要。相关循环、共享条件、失败关系和释放责任的精确性也未改变。

## 参考与尚未实施的推论

Rust的[增量查询说明](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html)区分输入变化与结果实际变化，并讨论稳定身份及追踪成本；[新trait solver缓存说明](https://rustc-dev-guide.rust-lang.org/solve/caching.html)明确保存已达到深度等资格，避免热缓存改变资源上下文的可观察结果。本研究借鉴这一结构，ZIL的ResourceLimit仍是失败，没有照搬Rust求解器的ambiguity含义。

[Polonius关系规则](https://rust-lang.github.io/polonius/rules/loans.html)的保守粗分析具有明确的潜在错误覆盖关系。它提示后续可沿实际读写支持切分求解范围；它没有给出省去ZIL其他责任条件的依据。跨编辑删除推导边、递归SCC自支持及共享条件相关性仍需要另外的完整关系控制。

本轮尚未实现跨编辑责任图的差分求解，也未实现单体结果的投影摘要或流式Debug摘要。Parse剩余预算之外的其他阶段仍用原完整请求键，所有文件仍读取，所有完整请求仍核验；因此局部成功不等于整个增量编译已经细粒度化。
