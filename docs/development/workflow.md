# 开发、复核与集成

## 从真实状态接续

先检查当前 checkout、`git status --short`、分支/worktree 和未跟踪源码，再读取独立看板：

```sh
git fetch origin refs/heads/goal:refs/remotes/origin/goal
git show refs/remotes/origin/goal:goal.md
git rev-parse HEAD refs/remotes/origin/goal
```

记录源码和看板各自的 SHA。离线数据注明时点。读取任务分支 `.task/<ID>.md`、所属规范段和相关模块；按需求向外扩展阅读，不把全部历史工单注入每个代理。旧提交号须能读出真实源码，未找到的对象、原始结果和未提交修改必须分别报告。禁止 reset/clean；禁止在编译中的 worktree 切分支。

## 分工以可验证行为为单位

每项任务先描述“哪个普通程序以前不能工作，现在应怎样工作”，再固定规范/源码基线、依赖、写集、成功例、最近反例和验收范围。编号来自 goal；永久文件和符号遵循[语义命名](repository-layout.md)。`.task/<ID>.md` 是短合同，不复制完整规范、看板和日志。

实现和独审使用用户指定的 sol high；疑难语义才交 Astra。无冲突写集并行，相交写集由集成者串行处理。公共 schema、根 Cargo/锁、正式验收门由集成者单写。代理可以提交限定测试结果；一个集成者持有本地重型构建/全量验收窗口，避免多份相同 workspace 测试争用资源。阻塞应给出最小输入、真实诊断、已排除原因及需要哪项裁决；其余独立工作继续。

以功能落点组织模块、fixture 和现有测试集合。每个测试解释它保护的行为/不变量，故障用例保留最小真实输入；不把“任务已完成”写进测试名，不为每名代理新增一个测试二进制。

## 修改哪个权威

| 变化 | 应更新的位置 |
| --- | --- |
| 语言行为、安全边界、拒绝条件 | `_zil_design.md` 及具名附件 |
| 阶段产物、依赖或稳定诊断 | `spec/`、`policy/` |
| 静态义务、正式案例或量化门 | `validation/`、`conformance/` |
| 已实现范围和用户用法 | `docs/guide/`、例子旁的 README |
| 长期选择及其理由 | `docs/decisions/<subject>.md` |
| 实时分配、依赖、阻塞和状态 | 独立 `goal:goal.md` |

接受性、ABI、错误/清理顺序和预算变化须列行为差异与最近反例，同步对应权威与实际消费者。生成器只产生未核代码；属性不制造权限；Verify 独立核验而不调用 Analyze/Types 求证。宿主 Rust 的检查不能替代 ZIL 安全核，也不能因实现困难隐式引入 RC、锁或堆盒。未实现义务不能通过改计划或永久标 Unsupported 消失；语义冲突只暂停受影响部分。

## 验证与证据按风险选择

| 改动 | 作者验证 | 集成时补充 |
| --- | --- | --- |
| 文档内容、目录、链接 | 引用、来源、生成视图；涉及工具则跑工具自测 | 独审迁移完整性和干净 checkout；不重复语言全量 |
| 机械迁名、测试组织 | 消费者闭包、原输入/选择集合、相应既有目标 | 无遗漏与无行为漂移；需要时覆盖原生入口 |
| 语言实现、ABI、责任或清理 | 真实 Source 正例/最近反例、独立 raw/Wire、预算与失败清理 | 按范围跑两配置全量/严格检查和两后端原生；公共接口变化覆盖所有消费者 |
| 成本或产品主张 | 冻结方法、同语义基线和真实计量 | 独占计时窗口、独立复核及既有产品门 |

验证选择及未执行理由写入收据。测试只对精确源码和实际环境负责；源码、输入、目标、feature、工具链或依赖变化后，复用旧证据需给出不受影响的理由。零选择/执行/断言、缺字段、Unsupported、超时、工具故障和失败字段不得 Pass。拒绝例匹配阶段/诊断且不能产出可运行程序。案例登记与执行分开，模型或手写 C/IR 不冒充生产源码行为。

原始运行使用唯一 `out/runs/<capability>/<RunId>/`；失败与修复不得覆盖同一目录。主树只晋升必要的 `validation/results/<capability>/` 精简结果：受测 SHA、范围、工具链/profile、实际命令/计数/退出码、失败与证据位置、未完成边界。每次集成交一份汇总和必要独审，不要求每个代理另存一份长期状态报告。原始运行是否随包交付按[交付说明](delivery.md)明确列出。

## 冻结、独审、合入

1. 作者提交候选；独立审核者不是作者，核对精确 SHA、写集、规范、合法/非法近邻、实际结果与责任清理。
2. 长期规则/决定/最小输入先归位；确认任务过程和源码可在已推送历史中恢复，再从交付树移除 `.task/`。不得在 main 保留工单或状态副本。
3. 冻结交付候选并运行适用检查及 `python3 tools/check-repository-layout.py --base <集成基线> --delivery`。后续变更列清差异，按影响补验；不拿旧 SHA 的成绩冒充最终树运行。
4. 集成者检查合入结果，推送后读回远端精确 SHA，更新 goal。切片通过不解除父任务依赖或完整发布条件；推送成功不等于验收。
5. 已合入分支在确认 main/固定 `archive/source-history` 可达、无唯一源码或未提交修改后退役。保留一个源码历史分支，避免按日期/任务增长的 backup 分支；不强推改写历史。

`node tools/handoff.mjs --check` 检查静态工程关系与交付记录，不读取实时 goal，也不证明语言正确性。默认输出和严格历史审核分开；旧 Unavailable/Unreviewed 不因文件整理变成 Pass。生成的 `data/handoff.json` 只是本地忽略快照。冷恢复、远端备份和审计附件见[恢复与交付](delivery.md)。
