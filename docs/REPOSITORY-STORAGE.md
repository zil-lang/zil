推荐保留一个日常开发仓库，分两步治理：

1. 源码仓库保留实现、规范、可运行测试/最小反例，以及简短结果和恢复清单；原始日志、IR/LLVM输出、全量文件清单、机器产物和归档统一外存。优先用同一私有GitHub仓库的Release附件沿用现有访问权限；高频或更大规模时再换对象存储。Release附件不进入Git对象库；它与当前配额已满的Actions临时artifact是两种存储机制。官方文档规定单附件小于2GiB，无单个Release总量/带宽限制，仍应按实际上传、重新下载与SHA256验证确认可用。暂未创建或发布Release。
2. 先归档并从空目录实际恢复核对，再迁出当前Git树的原始产物；仅保留每份归档的hash、大小、稳定下载入口、生成提交、命令、结果和工具链。详细逐文件清单随归档保存，避免清单本身继续膨胀。构建和普通测试不依赖网络下载审计包。七个被八处include直接引用的evidence输入须先移入长期tests/fixtures，涉及五个测试源文件；保留原输入字节和来源关系。

当前删除提交只能缩小新checkout，不能清除已有历史对象。先保留原历史，恢复日常轻量源码交付；如需完整clone也显著变小，在本轮施工收口后单独安排一次历史瘦身：先保存并实际验证完整审计bundle/旧提交映射，再协调所有分支、PR与工作树。历史重写会改变提交身份，须以具体可审方案另行确认。当前不新建平行主仓、不在施工中force-push。

测试整理与证据外存分开做：将新增测试按ownership、callbacks、syntax、wire等功能组织，工单号留在注释/来源索引。先选小组，把重复harness抽入support并合并适合一起运行的顶层target；比较测试选择、断言和编译/链接时间后逐步推广。保持有意义的进程隔离、特性配置、旧格式兼容对照和冻结oracle，不因编号旧而删除。

后续CI只需短规则：新增原始产物进入外存；测试不得直接include evidence；异常大文件必须有明确源码用途。已有历史失败记录保持可恢复，不为缩仓抹除。
