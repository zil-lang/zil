  impersonate ForeignCall. Verify retains its separate general foreign

## Concrete remaining boundary

Design profile196 explicitly permits several actual runtime positions from the
same callable generic. The captured-Fixed frontend still counts callable
receivers against generic declaration count in
`generic_stored_nominal.rs:223`, selects only one matching generic role and rejects
a second in `generic_callable_context.rs:202–216`, and Types independently rejects
two contexts for one Type ordinal in `helpers/source_life.rs:356–381`.
Thus `dispatch<life s,F:Fn(&Tag<'s>)->i32>(f:&F,g:&F,h:&F,x:&Tag<'s>)`
cannot use the new context lane even when the same shared closure is legally
supplied three times. Existing three-same-F non-Fixed tests do not prove this
qualified case. The author acknowledged the source consumer gap; this is an
acceptance gap, not an unsafe acceptance. A successor must bind context selection
to both original generic ordinal and actual parameter position, retain independent
runtime class namespaces, accept lawful shared alias and retain mutable-alias
rejection. Merely deleting the ambiguity check is insufficient.

Ordinary Value `give F` remains rejected by the original language rule. New
capture kinds, multi-role lending, general storage/dyn/async combinations and
persistent environments are not authorized by this finite consumer review.
Actual safety/source composition and accounting improve; Rust-equivalent
runtime/RSS, compilation/maintenance cost and a product-level net breakthrough
were not measured. Parent completion and formal root acceptance remain open.
