# Fixed SHA-256 source audit

Implementation baseline: `4cb3687127a1980b2ace965af9fdc8c8e5de93c5`. This record is a read-only source/dependency inspection and the authored adapter scope, not a measured speedup or an independent security audit of upstream RustCrypto. Build/test/performance receipts are produced separately by the integrator.

The selected registry dependency is `sha2 = { version = "=0.11.1", default-features = false }`. The release was published 2026-10-12, is not yanked at inspection, requires Rust 1.88, and is dual MIT OR Apache-2.0. The release archive checksum was independently recomputed and matched crates.io: `47d7069beb7d6ac7b9acd1039986e73443f24234f41074da099d6f994ac9ad19`. Its VCS record fixes RustCrypto/hashes commit `138dc5a05b93f8e49cda177fc6cfd7cc43673e5d`, path `sha2`. The manifest records URLs, exact bytes and hashes of the selected source excerpts. Saved `.txt` files are audit evidence, not an alternate Cargo vendor source.

`sha2/src/lib.rs` exposes the fixed-output Sha256 type and reexports Digest. The selected `digest 0.11.3` source shows safe `new`, `update`, `finalize`, and Clone-compatible fixed state. ZIL calls only those public safe operations; its existing SHA wrapper remains Clone and returns exactly 32 bytes. Hasher::finish, original Hash byte streams, budgets, Verify and all cache authority rules are unchanged. The previous scalar code is retained only under cfg(test), byte-identical to the baseline SHA-256 `722ba20d7403374f52d914a4380155d9bf5d7402536125b02c33627feeea7464`.

`sha2/src/sha256.rs` defaults to runtime feature selection. On x86/x86_64, `cpufeatures::new!(shani_cpuid, "sha", "sse4.1")` guards the call into the target-feature-marked SHA-NI backend. `src/sha256/x86_sha.rs` uses upstream architecture intrinsics and documented unsafe blocks; `cpufeatures 0.3.1` caches its detection in an AtomicU8 and contains the platform-specific CPUID boundary. These unsafe implementations are confined to external crates. The ZIL workspace/crate unsafe prohibition stays in force. Current host flags include sha_ni, sse4_1 and ssse3; this is capability evidence, not a runtime dispatch measurement.

When required x86 or AArch64 features are unavailable, the default selector uses upstream software compression. For the integrator's one explicit fallback control, use `RUSTFLAGS='--cfg sha2_backend="soft"'`; this is the first selection branch in the pinned source and requires no forced CPU features. Production must not set target-cpu=native or force the x86-sha selector. SHA-NI and software return the same SHA-256 bytes; the backend is not an identity input.

With sha2 default features disabled, alloc/OID are not requested. Direct registry dependencies are cfg-if 1, digest 0.11, and cpufeatures 0.3 on x86/AArch64. The inspected digest branch uses block-buffer and crypto-common, then hybrid-array and typenum; cpufeatures additionally declares libc for selected non-x86 platforms. Cargo.lock generated by the integrator remains authoritative for the final transitive versions/checksums. The separately inspected digest/cpufeatures releases in this manifest are not a substitute for lock resolution.

The existing `tools/check-architecture.mjs` enforces internal edges and external path dependencies; registry non-zil dependencies are allowed. Thus no internal policy change is necessary. The old dependency-free production documentation must change and offline packaging must account for the new locked registry crates. These changes, Cargo.toml and Cargo.lock belong to the integrator.

The key timer includes model traversal and buffer writes as well as SHA compression, and reports summed CGU intervals. Therefore the observed 85.7 ms opaque warm key total is neither pure hashing nor directly removable request wall time. A private profile can separate BufferedHasher update/finalization time from full machine_key time; final conclusions require paired complete requests. No timing was run by the adapter author.

The byte-compatibility statement applies to existing bounded compiler inputs and the FIPS message-length domain (<2^64 bits). Upstream ordinary length arithmetic can panic with overflow checks for a cumulatively enormous stream at or beyond 2^61 bytes, whereas the former scalar implementation wrapped explicitly. This out-of-domain FingerprintBuilder distinction is retained in the proposal/final report and is not claimed equivalent. Current compiler budgets are far below it; no budget or input guard was changed.
