# CP32 机制与完整成本静读诊断

审查者：`/root/frontend_incremental`

候选提交：`3ba131efdeffe85ba5fccd1c177745d812a6ce61`。

结论：**维持 NoGo，停止扩大实现、暂不采用。** 最大语料确实产生了部分留存和复用，但冷编译、公开编辑与内存代价抵消了收益。

本次仅静读已完成结果并作轻量数值汇总，无编译、测试、诊断运行或新增性能采样，无生产代码修改。

## 原 210 的 tree1024x8 已真实部分复用

读取完整原始 rows 后，两种容量下各 **10 个 B 序列**结果一致：

- 冷编译保留 **773 个模块、67,058,682 B（约 63.95 MiB）**，完整检查 9,222 个函数。
- 私有编辑复用 **6,940 / 9,222 个函数（75.25%）**，仍检查 2,282 个；Types 查询实际执行，属于模块 memo 命中。
- 公开编辑全量检查 **9,222 个函数、复用 0**。default 下从公开编辑恢复也全量检查，符合完整环境失效与单成功 epoch 的设计。
- 8192 的 unchanged、restore 等请求是**整个 Types 查询复用**；此时当前 memo 的 `eligible=false/checked=0`，同时仍保留 773 个模块，不能解释为资格失败。

## 成本：私有编辑有所下降，其他成本抵消

下表是 tree1024x8 **本窗内 CP32 / ee72 基线**的 `ratio_of_medians`；大于 1 表示成本增加。

| 指标 | default | 8192 |
|---|---:|---:|
| 冷编译 | 1.074083（+7.41%） | 1.018748（+1.87%） |
| 私有编辑 | 0.971682（−2.83%） | 0.926752（−7.32%） |
| 公开编辑 | 1.055856（+5.59%） | 1.409190（+40.92%） |
| 七请求进程 CPU | 0.999200（约持平） | 1.133334（+13.33%） |
| 进程峰值 RSS | 308,738 → 368,330 KiB（+19.30%） | 617,774 → 702,650 KiB（+13.74%） |

按既定五语料和四请求权重重算，完整组合与根初算一致：**default 1.003583；8192 1.060297**。五语料加权的七请求进程 CPU 分别为 **1.015849、1.123452**；加权峰值 RSS 分别为 **1.202026、1.138656**。默认组合没有建立净收益，较大 raw 容量也没有解决整体成本问题。

以上 RSS 汇总是按语料权重计算的单进程峰值中位数，不能当作多个进程同时运行的峰值；进程 CPU/RSS 对应完整七请求序列，不重新归给四请求加权组合。

## 与 CP29 的结构性差别

CP29 完整窗口中，tree1024x8 的 cold/private/public 都实际执行 Types，但 memo 保留和复用均为 0；CP32 已把这个机制缺口补成“有界部分保留且真实复用”。**这只能证明机制改进，不能把两个不同窗口直接当 CP32 对 CP29 的性能 A/B。**

公开编辑的全量检查计数支持“完整环境变化使复用失效”的解释；现有数据不能进一步把 CPU 回退精确归因于某个 clone、身份构造或 allocator，未借用 observer 数据作这种归因。

建议保留 CP32 的正确性与容量证据、冻结候选，**不合入默认路径、不扩大 64 MiB、不继续追求命中率**。
