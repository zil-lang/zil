## 原因与修复方案

初版虽然在 Expand 检查定义依赖、Analyze/Verify 检查真实 callee DAG，Types
的 `instantiate_helper` 仍在父 Builder 正文处理中递归进入子 Builder。
语言的有界调用依赖因此消耗同样深的宿主调用栈，早于语言限额就可能崩溃。

改为私有的具体实例计划，键是定义 `TemplateKey` 和具体 `ClosureId`。计划
只读取保留的 Core 正文与定义模块签名，在显式栈/表中解析 helper 依赖；按
先子后父顺序逐个完成普通 Builder。正文中的 helper 调用只可取已经完成的
实例，未计划依赖明确拒绝，不能再递归实例化。

调度器需尊重词法遮蔽和模块身份，跟踪 F 参数、普通局部别名、State 的 F
字段、已核 opaque factory 的具体返回及 helper 的 State 返回所提供的
类型身份。此类型身份仅决定需要预先检查哪个函数实例，绝不是借用来源或
权限证明；同一 ClosureId 的不同运行时实例仍由原 origins 和独立验证器
区分。所有具体正文照常检查，不能靠未核计划放行实际 Call。

依赖环、未知环境类型和无法有限计划的嵌套来源仍明确拒绝。实例依赖深度
使用现有 `max_call_depth`；图节点、边、深度、前沿、词法作用域与临时类型
形状均在实际访问/分配之前计费，不增加默认额度。helper CFG 循环合同不在
此修复中开放。

生产写集限已授权 `crates/zil-types/src/helpers.rs` 与待 root 注册的私有
`crates/zil-types/src/helper_plan.rs`；若需要额外状态则先按实际必要性报告。
公开 schema、Wire、Analyze/Verify 的独立轨迹语义、运行库和 LLVM 均保持。
