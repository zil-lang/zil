# 提案：编译器内建入口与数值转换

状态：讨论，未批准加入ZIL-LANG-1.2；本文件不改变parser或现行规范。

## 为什么考虑@

可以借鉴Zig的保留内建名字空间，让编译器原语与普通库函数一眼可区分。@并不天然表示编译期；当前#(...)已明确要求编译期求值，二者可以正交：例如候选@sizeOf::<T>()描述原语，#(...)描述何时求值。普通库函数仍应是普通名字，不因模型方便就升级为内建。

官方依据：https://ziglang.org/documentation/0.17.0/#Builtin-Functions 、同页@as、@intCast、@truncate、@bitCast。Zig的@intCast保持数值、目标类型来自结果上下文；越界是受安全检查的非法行为。@truncate显式截位，@bitCast重解释同尺寸表示。这里借鉴其分类，并不把Zig语法直接当ZIL规范。

## 必须先分开的语义

| 意图 | 建议边界 | 例子 |
|---|---|---|
| 给字面量/表达式一个目标类型 | 在类型范围内解释，不偷偷截位 | 123作为i16；128不能作为i8 |
| 保持数值的整数转换 | 编译期可证明越界则拒绝；运行期检查或明确返回失败 | i64到i16 |
| 截位/环绕 | 必须显式选择，结果与有符号解释固定 | 300到u8为44 |
| 位重解释 | 相同表示尺寸仍不足以证明任意目标有效，地址/资源不得绕过权限 | 浮点位模式与整数位模式 |

建议第一版先有一个规范的前置调用形式，例如候选@intCast::<i16>(x)。是否允许期望类型推导@intCast(x)、失败采用陷阱还是可恢复返回，要与ZIL现有错误和panic合同一起定；优化级别不得把安全转换变成未定义行为。这些拼写和名称均尚未生效。

## 123@i16应如何理解

它可以作为“值按目标类型转换”的专用后置语法候选，但不能仅凭“只有一个参数”自动把所有函数都后置：i16是类型，intCast是操作，checked/truncate/bit-reinterpret不是同一回事。

最近反例：

- -128@i8若采用通常后缀优先级，将先处理128@i8而越界；(-128)@i8才明确转换整个负数。需要明确负数字面量规则，不能临时看值改结合方式。
- a+b@i16通常只转换b；(a+b)@i16才转换和。应保持固定优先级。
- value@Vec<T>、value@&T、value@T?扩大了类型语法边界；不能让parser查询T究竟是类型还是函数后再猜语法。
- getValue()@i16必须仅求值一次；链式转换还要逐步保留每次失败行为。
- 123@i16几乎只展示了成功字面量，300@u8、负值转无符号、NaN转整数、资源到整数等才决定这个符号是否安全且清楚。

建议本轮保留为讨论；若后续采纳，先明确它只等价于一种检查转换，再增加糖。不要把“所有单参内建都能后置”作为通用规则。现有源码继续使用当前已实现语法。
