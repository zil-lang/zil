# 013：公开对话校准与闭包源面简化

状态：集成者于第四轮授权实施。基线为 draft03 `fbce9b8222d5fefe0f538c1e092a61604c482bcf`；本变更先于生产代码编辑记录。

## 来源与本轮裁决

已取得公开对话 https://chatgpt.com/share/6adab6de-6818-8322-9940-a0defbcbd15b 的连续54条正文（27轮），附件本体未取回。T53用户反对繁琐捕获，T54撤回强制捕获表、普通Copy快照和普遍强制give。T44至T54的多项语法是候选，并非逐项用户批准。完整逐项审计落在docs/DESIGN-RECONCILIATION.md，原始全文独立保存，不塞入日常源码包。

本轮用户要求闭包参考Rust且语法不能更麻烦；集成者据此明确发布1.3：

- 保留点模块路径、file/mod双入口合同、`-> R`返回、值泛型`::<T>`、名义记录与whole-base更新、无环境`fn(T)->R`、自动捕获与move、普通f(args)、词法self。
- 增加裸单参数`x => ...`与`move x => ...`；有参数类型时仍用括号；闭包可选`-> R`注记，参数和返回推导不能通过安全失败改换签名。
- callable约束采用`Fn(A)->R`、`FnMut(A)->R`、`FnOnce(A)->R`，内核参数仍为元组；旧`Fn<(A,),R>`源面以稳定迁移诊断拒绝，不长期维持两个规范拼写。
- 增加`.{...}`作为有期望名义类型的记录构造入口，归一化到既有Record；不新增匿名记录类型或隐式分配。
- 地址/Option结合方式保持当前1.2行为，明确的`(&T)?`与`&(T?)`分别作解析对照。起初提出的`&T? = &(T?)`修订因用户要求继续比较业界规则与频率而撤回待论；未进入本次生产解析改动。现行`&T?`仍表示`(&T)?`，本轮不得宣称争议已经结案。
- 闭包块的最后未加分号表达式返回值；末尾if/else的既有分支块递归处于同一值位置。缺失else、空块和普通语句尾为Unit；显式return与尾路径统一检查。末尾分号丢弃值；字符串/注释中的分号不参与此判断。具名fn和非末尾分支保持原显式return规则。

独立裸块语句尚无当前源面节点，本片不增加另一套块表达式。循环、defer、with等子体也不因位于闭包内部就自动产生返回。`@`继续为提案。

## 接口与实施边界

Syntax闭包新增`return_type: Option<TypeRef>`；Fn调用式约束正规化为既有Named/Dyn的参数元组和返回类型。闭包尾在专用解析路径正规化为既有Return，保留真实源span与词法token，不改普通Block结构。

013先沿用基线Core结构，闭包显式返回注记在展开时明确Unsupported，绝不丢弃注记。014串行接入`CoreClosureParameter.ty: Option<Type>`与闭包`return_type`，再完成类型推导和真实执行；013语法/展开通过不等于闭包环境已完成。

## 保留的候选差异

T50的冒号返回、`.<T>`、封闭匿名记录和通用callable的fn写法未采纳。T52只取得未覆盖字段的记录更新方案与当前whole-base不同，且其显式give前提在T54被撤回；聚合实施前仍要审查成本、消费和失败清理，不在本片暗改。
