# 168：具体闭包转发、拥有再捕获与保存

依据主树工单168与现行 `_zil_design.md` §7、§9.1–9.5；派工4ba11e1，生产基线45dbb920。
只推进语言，维持独立Verify与原预算，不引入隐式Box/RC或动态类型擦除。

## 当前断点与目标

现有自包含工厂只接受本函数新建的一个环境：Types拒绝工厂正文中的opaque工厂调用与转发，
Verify要求一个MakeClosure并拒绝有callable结果的Call。闭包可保存单独拥有资源，却不能将
另一个具体环境作为拥有字段捕获。拥有局部槽的替换须继续先准备RHS、再清理旧实例。

第一步支持有界依赖排序下的具体自包含工厂转发，保持原普通Call ABI、完整返回合同及实际
ClosureId；循环或无法唯一确定的隐藏身份仍须明确拒绝，不按布局或签名合并不同环境。
分别核对声明顺序、跨模块转发、未调用环境销毁、调用/参数错误路径和局部槽替换。

第二步使明确拥有的具体闭包可进入另一环境。共享/独占调用操作真实内联子环境；消费调用
转交该字段唯一责任；外层调用类别反映子环境实际使用。创建、调用、未调用销毁、补回和
失败出口不能丢失子环境的责任或来源。首片保持闭包参数/结果为现有有限Copy签名，不借此
开放逃逸Address/Desc捕获、拥有错误载荷回调签名或一般dyn。

## 公共接口请求与实现边界

工厂转发可沿用Call、TakeLocal及CallableReturnContract；公共schema若无变化不额外增加
opcode。源面opaque身份在转发及赋值上的区分必须保留，不能因为最终机器环境相同而抹去。
目前该身份在最终签名被消为ClosureId；须与root确认最小表示后实施相关归一化。

拥有再捕获需要可核的子环境借入/消费与递归清理。拟优先复用已有Address<Closure>调用路径，
由root评估最小捕获投影指令及现有TakeCapture准入的扩展。公共Type/IR/Wire、指纹、入口及
接口注册由root单写；施工者提交精确字段/消费者/最近反例，不自行扩写共享schema。

只有当实际元素载体与上述责任闭环就绪，才与167组合同质回调集合；不同closure表达式或
opaque声明不得按签名相同自动变成同一种集合元素，异构存储留在显式协议边界内。
