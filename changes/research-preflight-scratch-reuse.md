# Reuse bounded scratch during one complete machine preflight

Stage14 follows production 4bbbce204bb468d83eaebb78573c98104c3de348. Existing opaque machine output contains 2047 definitions with 8 blocks and 29 instructions each, plus a few other small definitions and one large caller. Current function preflight allocates label/SSA maps, CFG rows, dominance arrays and operand scratch again for every function, even during the validation-only warm path. This allocation count is a source observation, not a measured share of request time.

Create one FunctionScratch per validate_impl invocation and reuse it only for definitions with at most 32 blocks and at most 256 parameters plus instructions. This size selection never rejects an input: larger functions use a fresh temporary scratch and run the same checks, so large capacities do not remain in the small-function pool. Clear all map entries, CFG row lengths and work-vector lengths before each function. Retain only allocation capacity, never validated facts or prior model authority. Borrowed names/types remain within the current immutable Module/World lifetime.

Operand nesting is not part of the cheap size classification. If the operand-name scratch grows beyond capacity 256, drop that buffer after the function attempt, including an error. This only bounds retained allocation; it adds no operand pre-scan, input rejection or peak-work allowance. Declarations have no function body and keep the existing immediate return.

Reuse labels, definitions, successor/predecessor inner vectors, operand names and the existing dominator algorithm's seen/postorder/DFS stack/rank/idom arrays. Preserve the original definition pass, operation/SSA pass, CFG edge order and multiplicity, first-error ordering, dominance algorithm, phi checks and scheduling algorithm. COLLECT_SCHEDULE and validation-only scheduling eligibility stay unchanged; both complete preflight invocations remain where currently required. Do not change type/SSA limits, machine acceptance or ZIL Verify.

Scope: preflight.rs and focused preflight_validate_only_tests.rs controls, plus this proposal. A compact fresh-scratch versus reused-scratch control must alternate small/large/invalid functions, check exact errors/schedules and prevent stale labels, SSA definitions or graph state from crossing functions. Reuse existing dominance/phi/unreachable controls; no large generated matrix. Root exclusively builds/tests/measures; independent review is separate from implementation.
