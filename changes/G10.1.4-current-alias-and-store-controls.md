## Exact forwarding alias

The original impl103 negative is a valid Copy generic enum family alias:
`LegacyOption<T>{None,Some(T)}` with `Maybe<T>=LegacyOption<T>` and a scrutinee
already typed `Maybe<i64>`. Existing ordinary generic enum definition/instance
checks still prove the finite payload (ZIL-PACKAGE, ZIL-TRAIT; design §8.1.5
explicitly retains Copy generic enum support). The error is not an omitted type
argument in that actual scrutinee.

Historical103's finite proposal required concretization of bare generic alias
patterns. The successor bcfc0b1839de6be2e39e53aba973c11aaaf6372b added the exact
nominal-family forwarding path in `generic_alias::Alias::forward`, namespace and
pattern normalization. Its test is strict: one nominal path, same number/order
of arguments, each argument exactly its corresponding bare parameter. Ordinary
enum constructor/pattern checking follows. Fixed, reordered, nested or repeated
arguments do not acquire this rewrite. The old103 assertion was left behind;
6f74ec499dcb203f8319b3feabf8d0a2eb5f543f only renamed its formerly reserved
Option declaration to LegacyOption, without updating that historical assertion.

Keep the original source bytes as Source-through-Lower Success with one Verify
run. New native source reads Some(40) and the None branch's2 through an actual
Maybe<i64> parameter; alias and direct-family controls each run O0/O2 and return
42. Preserve all original unused/phantom/missing-type/duplicate-parameter/arity
negatives; add unused wrong alias arity, wrong Some payload arity and a repeated
argument family alias that cannot bypass its concrete constraints.
