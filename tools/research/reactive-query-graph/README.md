## 本轮不是再补一张反向索引

建议的生产结构是：

```text
稳定 QueryOwner
  + 当前 InputVersion / 上下文有效性
  + Declaration / Layout / Body / Effects / CT 等独立可观察结果
  + 本次实际读取的依赖 bond
  + 按高度组织的局部脏队列
  + 批量输入提交、逐层去重、等值截止
  -> 当前原始语义候选 -> 独立 Verify -> Lower / 机器码缓存
```

内容哈希应从“节点身份”分离为“当前有效性证据”，不能删除。包/声明身份、实例化参数、目标、规则、预算、名称查询的不存在事实、源码位置与 ID 重绑定都必须保持正确。已有函数 Types 和初始化投影缓存是可复用基础，不应再次重写一套重复缓存。

高度是依赖拓扑层级，不是 AST 嵌套深度或函数调用栈深度。队列只处理变化到达的节点；无需逐层扫描整张图，也不应强制无依赖任务等待全局同层屏障。静态拓扑、纯查询且一次批次输入稳定时，可以合并同层重复触发；动态增删依赖不能无条件承诺每个节点每代至多执行一次。

合法递归分析应先形成强连通分量，在分量内求固定点，分量之间再按高度传播。真实错误的查询环另行诊断，不能把合法的 1,200 层链因超过固定高度阈值而误报为环。

## 已实现的模型范围

`probe.js` 无依赖，可在 Node 或浏览器控制台运行。三种算法使用相同的查询定义和输入编辑：

- `height`：稳定节点、直接消费者通知、结果相等截止、按高度分桶、待执行标记/票号去重、动态新增依赖的按需稳定、结构变化时才修复高度。
- `pull`：按需递归验证依赖版本、每请求已验证标记、结果相等截止；不承担它不需要的反向边和高度维护。
- `invalidate`：反向索引批量失效、去重、干净节点直接复用；不承担多余的全图校验或高度维护。

三个实现都复用仍然存在的依赖记录。当前使用 Map/Set，尚未移植原 zit 的读取游标/侵入式链分配优化。错误恢复暂采用恢复输入并冷重建，非细粒度撤销日志。独立 oracle 每次从当前输入重新解释结果，不共享候选的依赖图、秩、版本或失效算法。

每个新进程执行同一组 2,730 次差分比较，包括 1,200 层链、菱形双源批次、600 次有向依赖换向、200 个随机动态 DAG、500 批语义形状编辑、等值截止、负向名称查询、事务中止、错误恢复及真实环拒绝。SCC 仅验证显式局部固定点查询，不包含自动 SCC 抽取。三个进程重跑不是 8,190 个不同测试。

## 冻结测量

Node v22.16.0；3 个新进程；每格先 2 次暖身，再测 9 个请求，算法顺序交替。下表为三个进程各自中位数的中位数，单位 ms。最大常规图为 114,948 节点、180,480 边；动态分支开启时为 196,864 边。

| 模型编辑 | height | pull | invalidate |
|---|---:|---:|---:|
| 单个私有体 | 0.052147 | 11.440182 | 0.111345 |
| 同批 64 个私有体 | 0.303901 | 7.661241 | 0.351672 |
| 只改模型注释字段 | 0.004757 | 10.505534 | 0.131115 |
| 名称空间高扇出 | 46.384470 | 47.007906 | 52.621259 |
| 全部私有体 | 130.655978 | 100.605484 | 151.636540 |
| 动态分支切换 | 26.385225 | 32.764564 | 28.272266 |

工作量比时间更有解释力：单体编辑时 height 和 pull 都只执行 8 个查询，但该 pull 模型还校验 180,158 条依赖；height 不做这轮递归校验。强反向索引基线执行 12 个查询，已经很快，不能拿较慢的 pull 结果声称相对现有生产编译器加速数百倍。全体编辑时三个算法都执行 98,561 个查询，height 比 pull 更慢；不存在免除真实重算的调度魔法。

这些查询只模拟源记录、声明/正文分面、类型/效果/代码输出之间的依赖，不执行 ZIL 词法、类型、借用、Verify、LLVM 或链接。没有真实 Rust 对照、编译器 RSS、生产工作负载频率，也没有证明冷编译/全场景加权收益。各进程内仍有 JIT/GC 及共享内存状态影响，时间只用于探索，不是统计接受门。

保留的纠正：初版 invalidate 比较臂对干净节点多做了递归校验，已修正，初版时间不进入冻结结论；随后去掉 pull/invalidate 不需要的高度维护，并把 height 秩维护限制为真实边变化。一次连续三进程外层命令达到 60 秒超时，第三份为空，不计成功；第三进程独立重跑后才纳入结果。见 `receipt.json`。

## 生产接入的完整研究边界

下一阶段应统一设计稳定 owner、输入快照、声明/布局/正文/效果查询边界、动态依赖及逐层队列，而不是先给旧整项目键套反向表。接入必须记录真实 query 执行数、边访问数、类型/分析工作量，并与同源码的全量路径逐项对拍。

必须覆盖私有编辑、签名/布局编辑、trait 候选新增或消失、CT 分支变化、递归/共享调用图、泛型实例化、资源密集输入、源码位置/ID 改变、预算 N/N-1、取消、失败恢复、缓存驱逐及恢复旧源码。对象缓存命中不代替当前独立 Verify。

端到端接受需要既有代表性源码的 cold / unchanged / single-edit / multi-edit / broad-edit 窗口、绝对等待时间、频率明确的加权结果、内存与真实机器行为。稀疏与密集变化的策略切换可以研究，但本轮没有实现或验证自适应切换。不能以调度微基准代替生产接受，也不能以一个密集格退化否定整条路线。

当前结论：值得继续完整架构研究；没有足够证据替换生产默认实现。
