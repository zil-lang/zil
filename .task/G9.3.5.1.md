# G9.3.5.1 · Source/Types and Store machine consumer

Parent: G9.3.5. Base: `f59929378642b684e81729814241b2ae117f5f68`.
Authority: `_zil_design.md` §8.1 and `changes/G9.3.5-ordinary-store-ownership.md`.
The integration owner runs Cargo and final acceptance; this branch contains the
Types and LLVM part of the jointly claimed task.

## Write-set decisions

- `zil-types` aggregate resolution retains explicit `manages` for Store fields
  and validates the full element, including unused declarations. Ordinary
  ownership shape, nested Package Product, ErrorUnion, direct and owning Package
  capture, and whole-place replacement now admit the already supported inline
  scalar/POD Store owner.
- `packages::supported`, `product::supported`, and owning-array eligibility
  remain the old container qualification. `StoreElement` remains independently
  qualified. Capture admission requires an actual move and a complete owning
  shape; a `Desc` or an array does not become an owner. Store callback elements
  call the legacy-only capture branch, so the new ordinary capture shape does
  not admit a Store as an element of a callback Store.
- LLVM's old Package/container admission is unchanged. The complete Product
  capture consumer accepts the new inline Store owner only after exact resource
  definition binding; teardown continues to use the Store allocation drop
  helper at the actual owned field/active branch.
- A captured Package may contain its Store owner below an admitted Tuple,
  Enum or ErrorUnion field. LLVM's capture representation now recognizes that
  full path and checks the complete value against actual resource definitions;
  the old Product/container predicates remain unchanged. The existing
  LargeCopy capture dependency pass reserves the complete type traversal
  before this representation check, and the new branch is absent for old
  profiles without an inline Store owner.
- Store resource registration follows inline Store owners hidden in complete
  Tuple/Enum parameters and returns, including a function that only relays the
  parent value. The new scan and its charge are selected only for trees with
  this inline Store family.
- New structural capture/replace walks draw on complete type snapshots already
  reserved at their call sites. Existing non-inline Store profiles retain their
  explicit paths and charges.

The next Source sweep exposed three responsibility paths beyond those shape
gates. Pattern inference now maps a taken Store arm into its actual payload
resource term, and concrete/generic Store call results can supply complete
Tuple fields. A Package field replacement whose old field is an owning Sum
stages the new value, emits `DropPackageField`, then commits and stores the
replacement; this retires the old tag-selected Store before overwriting it.
An inline-Store ErrorUnion temporary emits `DropErrorUnion` on every exit,
including the arm that leaves its Store error untouched. Direct owning Sum
capture uses `BorrowCapture` for Shared activation and `TakeCapture` for
Exclusive/Consume activation. Exclusive activation refills the same field with
`TakeLocal` then `WriteCapture` at each exit. The machine capture flag becomes
live only after the complete payload write, and direct Sum or Package<Sum>
environment teardown follows the active Sum drop helper. Analyze and Verify
must independently prove the exact capture debt, origin and exit obligations;
this task's static implementation is not their proof. Cargo and Source/native
verification remain NotRun in this worktree.

Subsequent real Source/native checks reached the machine replacement and
captured-Sum layout. A verified `CommitPlaceReplace` can now retire a direct
inline Store endpoint or a complete Product containing such a Store below
ordinary Package/Sum fields, after its staged RHS has succeeded. Its recipe
requires exact sealed resource definitions and the bounded whole root/path
scan; Array and Record ownership are still excluded. The backend's captured
Package field flag table now includes an owning Sum child, matching both the
environment flag allocation and tag-selected cleanup walk. Source inference
can describe an inline Store through an actual borrowed Managed head. Mutable
Sum locals use an internal Package slot, so closure formation resolves the
source capture through its actual `sum_slots` table and takes that complete
slot before constructing the environment. The initial inferred-Enum alias
normalization theory was disproved by a concrete Graph trace and removed;
strict aggregate equality remains. Root integration, rather than this task,
owns the final native matrix and Cargo evidence.

## Rust goals

Expressibility: ordinary owned Store values now follow the existing finite
Product/Sum path and concrete closure environment. Safety: explicit ownership,
active-branch cleanup and no array/container permission transfer remain required.
Runtime/RSS and compilation costs are unmeasured here. The finite owner path is
the expected safety and expression gain; no same-semantics Rust cost conclusion
is claimed.

The direct-shape Source sweep also exposed an owning ErrorUnion capture emitted as
`Load`, and a Shared Tuple capture pattern that read the entire owned Tuple
through an Address. The former now enters the complete owned-Sum transfer path;
the latter walks the actual captured Address and reads or borrows only selected
fields. An interleaved two-Enum<Store> FnMut Source exposed the prior footer's
LocalId-order violation: a newly refilled capture local could be newer than a
higher-numbered old-value local. The private capture cleanup planner now charges
and walks actual CFG Store/Take/Drop age, then schedules owned returns in reverse
successful initialization order while keeping lexical ScopeExit nesting. A join
with genuinely differing age orders still needs path-specific footer splitting;
no shared arbitrary order is accepted. Root owns the integrated Cargo/native
verification. The original interleaved Source is retained as a consumer and its
raw/Wire mutations target two actual capture indices.
