# G9.3.5.5 · Actual owned Tuple destructuring capture mode

Baseline `e200e0363f9604e1389e49b6aa626b1b0a8c39c9`, parent G9.3.5.
Goal snapshot `824591fe1781dfc5d71a2f0ef4e0e465d23ef34f`; design
§8.1.3.2, §9.1, §9.4 and `changes/G9.3.5-ordinary-store-ownership.md`.
Scope is Types source capture inference and an existing G9.3.5 consumer.

The original `ordinary-tuple-copy-companions.zil` returns a direct
`(Store<u64>, Marker, [u64;2])` capture from an `impl FnOnce` factory.
The previously built CLI reports Types Unsupported at the opaque kind check:
TupleBinding inference did not record the by-value owning child transfer, so
the closure was classified as `Fn`. The exact factory kind requirement stays.

TupleBinding inference now walks its real pattern against the complete actual
captured Tuple type. By-value bindings and discarded non-Copy Store-bearing
children make the capture consumed; reference bindings and Copy companions do not. This
handles a mixed pattern with a borrowed Copy companion without treating every
`ref` as a whole-pattern borrow. The walk and type snapshot debit the existing
request budget. The existing Source consumer asserts FnOnce, TakeCapture and
UnpackTuple; derived read-only, mixed and discarded-owner patterns assert
their actual Fn/FnOnce modes.

Evidence before root's single Cargo window: CLI
`zil check tests/language-readiness/G9.3.5/ordinary-tuple-copy-companions.zil --stop-after types --json`
reported `opaque callable kind adaptation is not implemented` at Types;
`rustfmt --edition 2024 --config skip_children=true` and `git diff --check`
passed. The prebuilt CLI predates this source change. No native result is
claimed here; the root integration owner will run Cargo, Source/Verify and
both backends on the merged commit.

Rust goals: the change strengthens exact owner transfer classification and
allows an ordinary owning Tuple closure to be expressed. It adds no implicit
allocation or new ABI. Runtime/memory parity, compilation cost against Rust,
maintenance cost and the complete four-goal product result remain unmeasured.

Follow-up on the integrated G9.3.5 Source/Verify targets: a conditional
missing FnMut capture refill exposed an early cleanup-order join rejection.
The private cleanup planner now propagates sparse definite/possible live owner
sets and actual before relations to the returning exit. A capture absent from
definite live at that exit is `E-UNINITIALIZED`; only a cycle in required
cleanup order remains Unsupported. This does not create a runtime authority
bit. The dual-capture raw/Wire shared-take neighbor now changes the actual
factory return kind claim and both consumer call instructions along with the
definition kind, so the independent Verify capture gate is reached with the
other callable metadata consistent. Root's one Cargo window will confirm the
revised scoped targets and the existing Source/native matrix.
