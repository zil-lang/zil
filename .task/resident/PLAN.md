# Resident memory and build latency

Baseline compiler production source: 3e4a2a2ae368380e86ea99da32d7f3eef68cf3b4 (resource-order candidate now integrated by PR75). Only a research example/stdio client is added: no driver or backend semantic rewrite, no new mainline command, and no external AI review. Existing CompilationSession raw snapshots are kept between explicit serial requests instead of discarded at CLI exit. Every successful request still runs current independent Verify and native build/link. This is a measured process-lifetime change, not a claim to have invented the existing cache.

## Frozen protocol
Original eight cases and source bytes from 95af0f0c205a0892e6087f5304ad9981461a7fed. Original group weights graph45/trait25/resource30 and mode/request weights remain unchanged. Five formal histories and one warm-up; Check/O0/O2 and cold/warm/body/edit-warm/signature/restore. Each history gets a new worker, which exits before another history; only that history's project disk caches are retained. Base starts the normal CLI for every request. Resident starts once, with the first measured request including spawn/readiness and every request including pipe round-trip through the completed response. Same two CPUs, Rust1.99.1, pinned LLVM and same release profile. All native .text bytes must equal base, output checks and runtime checks retain the original harness. No fresh-versus-warm subtraction across machines; no Cargo Fresh. Rust is not a new comparison arm.

Record peak/current RSS, raw query entry count, phase reuse/current Verify, full wall time and weighted absolute wait. Resident CPU time is not inferred from a process-global counter. Thirty-two raw entries bound retained top-level query count, NOT bytes of nested graphs or total process memory; this prototype is not a production daemon with a global memory-admission policy. Missing cells invalidate an aggregate. Syntax/type errors, recovery, explicit clear and oversized protocol commands are checked against fresh requests. No watcher, socket permissions, concurrent workspaces, persistent executable cache, lazy checking, JIT, hot swapping or background tiering is implemented.

## Blaze v2 and backend direction
Read at indexable-inc/blaze@a2b689f24c3bca40f4d02a949cd9e5b0adac9e12: docs/v2/plan.md, docs/v2/plan/design/compile-time.md, crates/blaze-query/src/lib.rs; the old docs/architecture.md explicitly says superseded, README assigns published performance figures to v1. Reuse actual ordered dependency observations and narrow interface/layout/body facts, not a global timestamp. Equal content can share immutable results; byte budgets, eviction and request isolation must accompany long-lived caches. Hash checks identify bytes, not safety authority.

Proposed ZIL development tier is verified frontend -> backend-neutral lowered ABI/drop model -> Cranelift per-function code, explicitly opt-in until scalar/aggregate/closure/FFI/cleanup parity passes. Release remains LLVM O2 with its independent runtime goal. Existing zil_llvm_api::model is owned machine data, not an LLVM pointer; a Cranelift producer should consume a semantic adapter, not parse printed LLVM text. One-function fragments must bind closure layout, drop logic, target/ABI, imported optimization dependencies and current rules. Copy-and-patch, tiering, JIT and incremental linking are later independent work, not functionality delivered here. The current resident worker cannot remove the observed large LLVM optimization unit by itself.
