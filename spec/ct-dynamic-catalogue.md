# CT dynamic metadata catalogue

`CtArtifactProgram.dynamic_catalogue: Option<CtDynamicCatalogue>` carries the frozen pre-generation Core inventory as untrusted data. `None` means a complete Core inventory has not been frozen; it is not an empty implementation set. The ordinary pure shape snapshot omits traits and providers and therefore cannot fill this field. The public `zil_driver::reify_frozen_core_dynamic_metadata` data bridge accepts an explicit immutable Core view and a shared remaining budget. Callers can attach this complete result as `Some`; the data projection itself does not authenticate a source or provider. A source-execution adapter must bind before execution and reject a different source snapshot. Its declarations retain stable declaration identities, complete original mixed formal order, super applications, structural and callable obligations, type and constant equations, associated definitions, original method definitions and their exact specializations. Interfaces retain complete applications, associated results, effective slots and their contracts. Vtables retain implementation witnesses, actual receiver domains, port bindings and cleanup routes. Actual function instances and retained result source bindings remain attached to their original module and function identity.

Every runtime `Type` payload becomes a `CtDynamicTypeId` edge into `types: Vec<CtDynamicTypeNode>`. This metadata DAG preserves all constructors, complete nominal and opaque payloads, qualifications, class maps, callable relations, retained leaves and actual dynamic interface references. A type node may reference only earlier type nodes; catalogue records may select any existing node. References are local relocation data, never stable semantic type identities. Original nominal declaration and instance inventories remain separate catalogue fields. Implementations and witnesses are inventory, not part of an unrelated Type's semantic identity.

`CtStorageSource` preserves the five runtime source expressions with the same meanings described in [storage-source-atoms.md](storage-source-atoms.md). Its `OwnedView` and `Static` leaf fields select complete metadata Type DAG nodes. `CtDynRetainedPortBinding` still carries only real `StoragePosition` leaves. No implicit load, address taking, mutable weakening, static provenance or owned-region permission follows from a catalogue row.

The source bridge reads the immutable Core inventory, builds every actual Type node and preserves every optional unknown field. It does not replace absent metadata with an empty proof. Encoding, decoding, full fingerprints, comparisons and clones account for all catalogue fields, paths, strings, constant bits and referenced Type nodes before allocation or traversal. Dynamic recipe transport also has a finite 128-level ceiling within the selected call-depth limit. The independent CT structural consumer checks the complete inventory, reference range, postorder edges, graph depth and work/node/temporary-byte limits before the full frozen-artifact comparison. The driver retains only a private immutable inventory cache; every later clone pays its complete traversal and storage cost again.

Catalogue admission does not authorize reflection, declaration visibility, a provider, trait implementation, runtime storage access or cleanup. Such consumers must independently check their actual source, signature and CFG obligations. In particular, the existing `CtTy::Type`/`CtTypeRef` execution and query bridge retains the strict boundary stated in `_zil_design.md`'s CT4/CT5 scoped-Type contract: dynamic and Task type queries require their separate complete context consumers. The metadata DAG is not silently converted into an admitted `CtTypeRef`, a runtime value or a provider certificate. Unsupported consumers reject explicitly.

The runtime and CT version numbers remain work-in-progress until the joint schema publication. No reader guesses an earlier source-position encoding or treats an empty source list as `Static`.

The catalogue retains `CtDynInstantiationScope`, witness `to_context` and function-instance `header_embedding` separately. Lexical fixed/invocation classes survive even when they have no physical runtime-header occurrence. An explicit embedding may map two lexical classes into the same outer Context; this does not erase their distinct local identities or remove unused original formals. The original declaration's complete implicit-lifetime inventory retains each exact recipe root, structural path and Address/Description/LifetimeArgument kind. A `Desc` recipe's lifetime remains an explicit optional `CtDynLifePattern`, including `ImplicitDeclaration`; `None` remains unknown. No Static binder is introduced.
