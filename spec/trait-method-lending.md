# Trait method lending

Ordinary static nominal traits may declare method-local life binders on shared or mutable receivers. The finite profile returns an existing shared thin address directly or inside the canonical built-in `Option`; its referent is an existing Copy type or an ordinary associated `Item`. An associated Item may be a complete owning Package; its shared address carries no Item ownership or Copy permission. The method life variables identify actual input positions, including lowered receiver position 0. Each invocation substitutes its actual inputs. An implementation may alpha-rename local binders but must preserve the complete relation, receiver mode, nominal trait/provider identity, associated substitution, coherence and visibility.

Definitions, implementations and generic consumers, including unused definitions, retain bounds, scope and loan checks. The implementation body must prove returned roots lie within the declared relation. A shared result borrowed through a mutable receiver retains its parent loan through last use. While live, it prevents an overlapping call, movement or overwrite. Distinct receivers and use after last use remain valid; local, wrong-parameter and retired-root returns are rejected. Analyze and Verify reconstruct actual CFG and call provenance independently.

This profile includes ordinary nongeneric traits with an ordinary `Item` declaration (and optional explicit bounds), concrete nominal implementations, existing type-only nominal generic implementations and generic functions consuming the trait bound. Method generics in this profile are life-only. It does not grant GAT, trait/impl life parameters, default body, mutable or fat Option payload, blanket selection, dyn, async, capture or new storage capabilities. The existing generic, default and inherent cases follow their own established contracts.

A type-only generic implementation may write bounds on its associated type equation, including bounds beyond the trait declaration. Every such bound is proved from the complete symbolic equation and the implementation's own declared premises when the implementation is defined, even if no instance is called. The trait's declared bounds are proved independently and remain the only associated bounds exposed to a generic consumer. The trait parameters and implementation parameters retain their separate binders, and module paths in both the implementation premises and associated bounds resolve to their actual nominal providers. An equation cannot establish its own premise; active equation cycles and overlapping implementation heads remain errors. This does not admit generic associated type members, implementation life/const binders or projected implementation heads.

The `std.iter` interface and cross-module consumers preserve provider/Item identity and the per-call lending relation. Raw/Wire mutations must be rejected by independent checks of actual provenance, not producer annotations. Scans, maps, substitutions and queues consume the current request budget. Governing rule: `_zil_design.md` §18.1.

A concrete Package receiver may own the actual `Store<Item>` from which a thin shared Item address is yielded. The full manager remains pinned by the live result, including while Some is saved before its payload is projected. Its ordinary ownership and cleanup obligations remain in force.

An ordinary generic helper may combine life binders with independently bounded type parameters and forward a shared address or Option address result. Each type parameter carries direct nongeneric nominal trait bounds, the existing structural Copy bound, or both; at least one nominal premise is required for this lending profile. Multiple bounds must select a unique method and associated member by their actual declarations. Bound order and companion type parameters do not merge provider identity or binder domains. The helper's definition follows the selected declaration's method-local life relation through the actual receiver and arguments into its own allowed inputs. The generic body is checked even when unused, including each companion's declared capabilities; concrete specialization cannot supply missing definition-time premises or provenance.

`std.iter.LendingIterator` declares `type Item;`. Its `next_copy` convenience function separately requires `where I.Item:Copy`. A free function's direct associated projection may carry this explicit Copy where obligation; the lexical trait bound selects the actual associated member, and both symbolic checking and every concrete call must prove it. This does not grant Copy from an unbounded Item or from a trait implementation alone.

Ordinary lazy owning adapters, independent structural Value/SyncDrop obligations, full generic trait arguments and borrowed/owning callback consumers follow [ordinary values and synchronous iteration](ordinary-values-and-cleanup.md). A direct sealed Store lookup and a static helper returning `Option<&'a T>` retain the actual manager and argument life relation, including through a complete inline Package field path. Structural companion bounds do not select a nominal provider or change the returned loan.
