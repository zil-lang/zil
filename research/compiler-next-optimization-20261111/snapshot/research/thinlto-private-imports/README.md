# ThinLTO 预优化复用后的私有导入实验

## 为什么

默认 ThinLTO 没有实际导入本轮跨分区函数；原预算内完整导入补回了 56／224 个实际函数体，却仍未通过相对主线的运行质量门。真实 LLVM 内联诊断发现，`available_externally` 导入无法获得原 ZIL 私有、单调用者实现的 `LastCallToStaticBonus`。本实验检验在预优化结果复用后保留原私有导入语义的作用；不调整内联阈值，不附加 `alwaysinline`，不改变算术或原复制预算。

这是一个仍在实现与复核的研究候选，尚未构建、执行或通过质量门。先前四个候选的 NoGo 不因本实验而改变。没有生产采纳或编译速度收益结论。

## 实现边界

复用已验证的主线 `99035931d358add0eaed6d4535035c38413701dd` 与严格导出器 `2549cbec8e1f3096d4c8c8a960459c83095ad13d`，不重新构建 Rust 编译器本体。独立 C++ 插件通过 LLVM 23.1.4 官方 `--load-pass-plugin` 接入，只在 `ThinLTOPostLink` 的 early simplification 扩展点运行；保留随后完整的 O2 管线。插件从实际 lld 的导出符号解析 LLVM API，不链接另一份 LLVM 动态库。

当前 Rust 模型证明和实际 prelink 依赖证明共同给出唯一 owner、原 Allowed 集、原成本总界及 Required 函数体。插件只处理实际、已准入的 AE 定义，逐个 Use 核实它确为直接调用的 callee；地址参数、别名、元数据地址和 COMDAT 等研究范围外输入拒绝。允许项改名为 `zil.import.<destination-unit>.<canonical-name>` 并设置 Internal，不增加另一份函数体或更改其指令；原 canonical owner 保持在原模块。

每个后端均新建 started／完成收据并保存前后 IR，零导入的后端也必须出收据。外部检查重新核实 `.3.import.bc` 完整性与预算，再检查实际 hook 的八份收据及完整 IR：反向还原批准的名称和链接属性拼写后，全文必须相同。该证据绑定当前源码检查收据、实际位码、插件二进制和冻结协议。

LLVM 当前原生缓存键没有绑定插件二进制与环境许可。本实验因此每次新建空缓存；没有插件 warm-cache 复用结论。未来若生产化，缓存域必须显式绑定插件与配置，不能沿用本实验身份当作缓存能力。

## 验证与退出条件

先做源码与 API 独审、插件构建和必要的有效地址反例控制，再冻结并执行原两个规模的质量对照：6 次干净编译、54 次原生进程，其中 36 次正式计时，固定两 CPU／两任务；语料、输入、运行次数与六种排列次序不变。每格仍要求 B/A ≤ 1.10 且 Rust/B ≥ 0.90，保留所有样本和首次失败。

本阶段的编译墙钟含大量证明、哈希与诊断，不作为编译性能门。通过运行质量后，才有依据测量去除诊断后的完整编译请求与多点修改；不以某个 pass 的变快替代用户等待时间。

此目录全部 Python 和 C++ 源将按精确字节冻结；插件有独立构建收据，Rust 导出器复用已有构建绑定。冻结后不在原目录追加可执行源码；后续失败修复另存完整版本与新运行身份。
